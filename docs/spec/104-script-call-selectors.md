# Spec 104：`2Dh CALL` 的選擇子只有五個有動作

狀態：READY（分派器逐條讀完）

## 一句話

`2Dh CALL` 的處理常式只認五個選擇子，**其餘一律什麼都不做**——所以認不出來
的選擇子不是「還沒接」，是原版本來就沒有動作，不能讓它擋住移動。

## 分派器（overlay-03 `3026h`）

```
302F  取一個運算元
303C  ax = 運算元的值（overlay-07 0052h）
3047  ax -= 7FFFh
3050  ax == AC91h（選擇子 2C90h）→ 重算地形暫存 DS:6A0Fh（overlay-30 003Eh）
                                   若 DS:4398h ≠ 0 且五個旗標任一非零，
                                   呼叫 overlay-36 0025h 與 overlay-25 00DEh，
                                   再把那五個旗標清成 0
30B4  ax == 1（選擇子 8000h）    → overlay-07 00A2h，引數 1
30C3  ax == 2（選擇子 8001h）    → overlay-07 00A2h，引數 0
30D2  ax == 3A04h（選擇子 BA03h）→ 依 DS:8292h 是 8 或 0Ah 播兩段之一（0027Fh:0）
30FA  ax == 401Fh（選擇子 C01Eh）→ overlay-07 00A7h：依朝向走一格、邊界繞回
3106  ax == 4019h（選擇子 C018h）→ DS:495Bh == 1 時重算牆的暫存 DS:6A0Eh
3126  其餘：直接返回
```

實際出現在 ECL 裡而**沒有動作**的選擇子至少有 `0806h`、`2C4Eh`、`2C51h`、
`C003h`、`C009h`、`C01Bh`。

## 為什麼這一條要緊

remake 把 `2Dh` 當成前端事件傳出去，而前端一遇到事件就停下來、不移動。
樞紐那幾張圖**每一格的入口 0 都有一個 `CALL`**（spec 103 的掃描：ecl6/25、
ecl7/26、ecl8/27、ecl8/29 各 1024 格全部停在 `2Dh`），所以隊伍一步都走不動：
量到的是一趟 20 萬個 tick 裡走了 36 步，其中 10 萬次在「走路」、10 萬次在
「格子事件」之間空轉。

接上去之後（`applyTransitionResource` 吃掉 `2Dh` 再續行），同一份治具走到
5 張地圖、7 個 ECL block（0、8、11、20、21、**26**、**27**）。

## 順帶修掉的三個

1. **邊界上限 8 太小**。`2Dh` 也走這條路之後，一次移動可以連續吃掉十幾個
   邊界，8 會誤報成硬失敗。改成 64。
2. **離開旗標要在共用的那一支清**。`DS:6DD5h` 原本只在事件掃描那條路清掉，
   `2Dh` 改走消費路徑之後就沒人清了——實測會在城區與貧民窟之間換區到
   上限。清的動作移進 `applyScriptCall`。
3. **數量 0 的 `LOAD MONSTER` 不該報錯**。貧民窟的隨機遭遇把數量放在
   `DS:9808h`，由區塊的入口 4 算出來，而換區時原版是先跑入口 0 再跑入口 4
   （spec 025），所以入口 0 讀到的還是 0。報錯會讓玩家從起點往西走一步就
   掛掉。現在跳過那種 descriptor；一隻都沒放成就不開戰鬥。
   **OPEN**：原版對數量 0 的處置還沒讀。

## OPEN

- `8000h`／`8001h` 那一支（overlay-07 `00A2h`）做什麼。
- `BA03h` 播的兩段是什麼（`DS:263Ch`／`DS:263Eh`）。
- `2C90h` 那一支後半段的五個旗標（`DS:82A6h` 等）與兩個呼叫。
