# Spec 105：野外地圖——座標、三張圖怎麼接、地點表

狀態：READY（座標系統、拼接條件與三張邊界表、四張表的版面與內容、
20 支地點腳本的入口與第一句、每一步的移動）；
DRAFT（野外畫面與 GEO block 6 的對應細節）

## 一句話

野外不是 16×16 的格子圖：隊伍的位置存在 `DS:49C3h`（X）與 `DS:49C4h`（Y），
由三張 ECL 區塊（25、26、27）由西到東接成一條，每一格「有沒有東西」用四張
連著放的表查出來。

## 座標與拼接

`49C3`／`49C4` 不是格子座標——碼頭設的值是 (7,29)、(13,27)、(9,29)，Y 超過 15。
X 的範圍是 2..15，Y 的範圍是 8..33。

三張圖由西到東是 **25 → 26 → 27**，跨圖的條件寫在每一張的入口 0：

| 從 | 條件 | 到 | 新的 X |
|---|---|---|---:|
| 26 | `49C3 == 15` 且 `49C4 != 25` | 27 | 3 |
| 26 | `49C3 == 2` 且 `49C4 != 31` | 25 | 14 |
| 27 | `49C3 == 2` | 26 | 14 |
| 25 | `49C3 == 15` | 26 | 3 |

（`49C4 == 25` 與 `49C4 == 31` 兩個例外是牆／河，不給過。）
`49C4 <= 2` 另有一支（北緣），還沒讀。

移動本身也是 ECL 自己做的：入口 0 先把 `49C3`／`49C4` 抄進 `DS:00FBh`／
`DS:00FCh`，再用一張八支的 `ON GOSUB`（ecl7/26 `9A18h`）依方向各對那一對
±1——**八個方向，正好是原版的八方位移動**。

## 地點表：四張表連著放

入口 1 用四張表把座標換成地點編號，再 `ON GOTO` 分派：

```
6E7C = 0；6E79 = 0
迴圈：6E7B = 每列數量表[6E79]；6E7A = Y 表[6E79]
      Y 表[6E79] == 49C4 → 找到這一列
      否則 6E79++、6E7C += 6E7B
找到列之後：在 X 表的 [6E7C, 6E7C+6E7B) 裡找 == 49C3 的那一項
找到就 6E79 = 地點編號表[6E7C]，ON GOTO 6E79
```

四張表的位址（從靜態追蹤的 `GETTABLE` 第一個運算元讀出來）：

| 區塊 | Y 表 | X 表 | 每列數量 | 地點編號 | 列 | 地點 |
|---|---|---|---|---|---:|---:|
| ecl6/25 | `ADD6` | `ADDE` | `ADF5` | `ADFD` | 8 | 23 |
| ecl7/26 | `B04A` | `B053` | `B061` | `B06A` | 9 | 14 |
| ecl8/27 | `ABA6` | `ABAB` | `ABB4` | `ABB9` | 5 | 9 |

四張表是連著放的，所以**長度從位址差算得出來**：列數 = X 表 − Y 表，
項目數 = 每列數量表 − X 表。三張圖都對得起來（每列數量加總 == 項目數）。


## 移動怎麼接（已落地）

前端只做三件事，其餘交給 ECL：

1. 把八方位的方向寫進 `DS:033Dh`——那正是 `9A18h` 那張 `ON GOSUB` 的索引
   運算元（記錄本體是 `26 01 3D 03 00 08 …`，運算元碼 1 代表記憶體參照）。
   索引**從 0 起算**（引擎 `machine.go` 的 `targets[index]`），八支照
   `branch_targets` 的原始順序是：

   | 索引 | 目標 | 做的事 | 方向 |
   |---:|---|---|---|
   | 0 | `9A9Dh` | Y−1 | 北 |
   | 1 | `9AA7h` | Y−1、X+1 | 東北 |
   | 2 | `9AB0h` | X+1 | 東 |
   | 3 | `9ABAh` | X+1、Y+1 | 東南 |
   | 4 | `9AC3h` | Y+1 | 南 |
   | 5 | `9ACDh` | Y+1、X−1 | 西南 |
   | 6 | `9AD6h` | X−1 | 西 |
   | 7 | `9A94h` | X−1、Y−1 | 西北 |

   所以四方位是 **0、2、4、6**，也就是朝向乘二。
2. 把 `DS:6DC9h` 清成 0，跑入口 0。
3. `DS:6DC9h` 不是 255 就把 `DS:00FBh`／`DS:00FCh` 收回 `49C3`／`49C4`，
   再跑入口 1。

`6DC9 == 255` 代表「這一步不給走」：三處寫它的地方分別是撞到不可通行表、
Y 到北緣、跨圖的例外座標——三個獨立的來源都是同一個意思。

量到的效果：治具走到的地圖從 5 張變 8 張、ECL block 從 7 個變 8 個
（多了第三張野外圖 25）。索引改成 0 起算之後，往東走一步只加 X
（先前 X 與 Y 會同時加一，也就是每一步都走成東南）——
`TestWildernessFacingIndexPicksTheCardinalArms` 釘住這個對應。

**野外的一步是兩件事一起發生。** 引擎照一般規則在載入的 GEO 上走一格
（進野外時 `LOAD FILES 6, 6, 0`，所以走的是 GEO block 6），而這一區的
入口 0 同時把野外座標往前推一格。兩者不是二選一：

- 野外那三個 ECL 區塊都沒有 `CALL @C01E`（由腳本走一格，spec 104），
  卻有七次 `CALL @C018`（用 `6A0Bh`／`6A0Ch`／`6A0Dh` 重算面前的牆）——
  重算牆表示引擎那一邊確實在動。
- 那三個區塊裡寫 `C04Bh`／`C04Ch`／`C04Dh`（＝ `DS:6A0Bh..6A0Dh`，spec 106）
  的地方都在**地點腳本**裡，是進區域前擺位置用的，不是每一步。
- 所以每一步的 GEO 移動是引擎預設行為，前端不該把它換掉。

前端要做的只有三件：走之前把方向寫進 `DS:033Dh`、把 `DS:6DC9h` 清成 0；
入口 0 跑完之後，`6DC9h` 不是 255 就把 `00FBh`／`00FCh` 收回 `49C3`／`49C4`。
牆擋住的時候兩個位置都不動。`TestAWildernessStepMovesBothPositions` 釘住這個
配對；先前前端把野外整條移動路徑換掉，隊伍在 GEO 上不動，Y 也就一路走到 34、35。

## 野外是一張把 GEO 平鋪上去的迷宮

上一節那條規則（牆擋住的時候野外座標與 GEO 格子都不動）有一個直接的推論：
**兩者的差是常數**。量一次就得到

```
GEO X = (野外 X + 位移X) mod 16
GEO Y = (野外 Y + 位移Y) mod 16
```

所以野外的可通行性就是那張 16×16 的 GEO 圖**平鋪**上去的結果，可以直接對
野外座標做 BFS，判定用 `CanMoveDungeonWrapped`——和遊戲自己走路用的是同一支。

三張野外圖載入的 GEO 是 **GEO5/4、GEO5/5、GEO5/6**（`LOAD FILES (4,4,0)`／
`(5,5,0)`／`(6,6,0)`；區塊編號在八個 GEO 檔裡全域唯一，spec 043）。它們各有
108／111／112 格可走、5–6 個連通元件——**不是隨便走得通的平原**，所以要走到
指定座標一定得規劃。第三欄不是 `FFh`，所以同時還載入 `BACPAC` 背景圖庫。

三件事會讓「照著方向一直走」失敗：

- **位移不是固定值，跨圖會重算。** 跨圖時 ECL 把 `49C3` 設成 14 或 3，而 GEO
  只是往旁邊走一格，所以位移的 X 分量整個換掉。從東邊登陸點往西走的那一條，
  量到的是 27 `(6,4)` → 26 `(10,4)` → 25 `(15,14)`。
  **但決定它的不是「從哪一列跨」**：從圖 27 的西緣七個不同的列跨到圖 26，
  位移一律是 `(10,4)`、一律落在 X=13，只有落在哪一**列**不同（因此可能落在
  迷宮的不同連通元件）。**跨出去再跨回來也換不到另一座迷宮**：往東與往西的
  推移大小相同、方向相反，來回一趟剛好抵銷；探索器的上限從 6 拉到 24 實測
  走到的地點一格都沒多。

  真正決定迷宮的是**當初從哪一條航線下船**。三條航線量到的落點與位移是：

  | 航線 | 野外圖 | 落點 | 位移 |
  |---|---:|---|---|
  | EAST | 27 | (9,29) | (6,4) |
  | WEST | 26 | (7,29) | (8,4) |
  | BAY | 26 | (13,27) | (2,6) |
- **地點格要繞開。** 踩上去就會跑那一支腳本，而地點腳本動不動就 `NEWECL`
  把隊伍帶離野外：實測從圖 27 往西跨到 26 之後第二步就踩進 (11,28)，
  直接被送去區塊 18。繞不過去的時候才允許路過。
- **路線要整條記住。** 每一步重算「到任何一列的邊界最短的那一條」的第一步，
  目標會隨著移動改變，於是繞開地點的規劃等於沒做——同一個實測案例裡就是
  這樣一路往西踩進 (11,28)。
- **踏出去那一步一樣會被牆擋。** 跨圖是「走到某一個 X 再踏出去」，只看 X 對
  不對就會站在邊界對著牆按前進：實測有一趟站在圖 26 的 (2,23) 按了七千多次。
  邊界那一格要先問 `CanMoveDungeonWrapped` 讓不讓踏出去，另外配一個「位置
  連續幾個 tick 沒動就換目標」的看門狗。

**哪一座迷宮走得到哪些地點，全部列舉過了**（`workplace/wildreach`：16×16 種
位移乘上每一種入口列，圖 25 是 8192 種、26 是 16384 種、27 是 8192 種）。
每一個地點都有**兩成以上**的起始狀態走得到——最低的是圖 25 的 (2,33)（18%），
最高的是圖 27 的 (7,16)（53%）。所以「走不到某個地點」永遠是位移的問題，
不是那一格進不去。

反過來說，**一組位移能走到的地點很少**，而且模型與實跑對得起來：

| 航線 | 位移鏈 | 進圖 25 的落點 | 圖 25 上走得到的地點 |
|---|---|---|---|
| EAST | 27 `(6,4)` → 26 `(10,4)` → 25 `(15,14)` | (12,31) | (8,24)、(12,30)、(11,31)、(12,31)、(12,32) |
| WEST | 26 `(8,4)` | 走不到 | — |
| BAY | 26 `(2,6)` | 走不到 | — |

EAST 那五格**正好等於**列舉出來的結果（位移 `(15,14)`、從 (12,31) 進來），
所以探索器在那條航線上已經走到能走的全部。WEST 與 BAY 更極端：落點分別是
(7,29) 與 (13,27)，那兩格自己就是「回文明區的船」，而且從那裡一格都走不出去。

**所以區塊 19（(10,9) 龍穴）與 28（(3,32) 前哨站）在目前這三條航線下走不到**
——這是量出來的，不是還沒試夠。

## 換口袋靠進出區域，不是靠走路

位移不是野外自己的性質，是「GEO 位置」與「野外座標」被**分別**寫的結果。
`ecl6/25` 在 `A48A..A4C0` 成對寫 `DS:4A18h`／`4A19h`：

```
A48A  15 → 4A18 ；A490   3 → 4A19
A49A   0 → 4A18 ；A4A0   2 → 4A19
A4AA   0 → 4A18 ；A4B0   9 → 4A19
A4BA  11 → 4A18 ；A4C0  15 → 4A19
A4F4  LOAD FILES 25,2,255      ; 區域圖 GEO6/25
A4FB  SAVE @4A18 → @C04B       ; 把 GEO 位置擺回去
A502  SAVE @4A19 → @C04C
A514  NEWECL 25
```

`4A18`／`4A19` 是**進區域圖時要站的 GEO 格子**，四組候選 (15,3)、(0,2)、
(0,9)、(11,15)。圖 26 有三組（`A50B..A531`：(2,3)、(10,13)、(13,6)），
圖 27 有四組（`A273..A2A9`：(0,3)、(6,15)、(12,15)、(11,0)）。

這也解釋了野外那兩張圖的兩種身分：`LOAD FILES 4,4,0` 載的 GEO5/4 是**地形**
（在上面走，位移把它平鋪到野外座標上），`LOAD FILES 25,2,255` 載的 GEO6/25
是**區域圖**（62 格分成 42 個互不相連的區塊，靠上面那四組座標各自進去）。

**選哪一組是擲的**：`A472 RANDOM 3 → @6E7E`，接著 `A478 ON GOTO @6E7E` 四支。
而進來的入口是一句原文——

```
A425  PRINTCLEAR 'YOU HAVE FOUND A SMALL DARK CAVE.  WILL YOU ENTER?'
A44E  HORIZONTAL MENU
A460  ON GOTO @6E79 → [A46C 進洞, ADC9 不進]
A46C  SAVE 255 → @4A9E          ; 進區域圖，入口 0 的野外那一段整段停掉
A472  RANDOM 3 → @6E7E          ; 四個落點擲一個
```

`4A9E` 就是入口 0 第一行 `9914 COMPARE @4A9E, 255 → EXIT` 比的那個旗標：
**255 代表現在在區域圖裡，野外的每步處理整段不跑**。回野外走另一條
（`AB2A LOAD FILES 4,4,0`、`AB31 SAVE 0 → @4A9E`、`AB3B NEWECL 25`）。

所以進出一次區域，`C04B`／`C04C` 被重寫成擲出來的那一組，而 `49C3`／`49C4`
沒有跟著動——**位移整個換掉，而且是隨機的**。野外因此不是一張連通的圖，是
一組口袋；換口袋的方法是**答應進洞再走出來**，不是走路。這也是 (10,9) 與
(3,32) 唯一的路：多進出幾次，總會擲到把它們含進去的那一組位移。

`cmd/pool-game` 的探索器照這三條走（`wilderness_explore_test.go`）。
`TestTheWildernessWalkReachesTheWesternSheet` 從東邊的登陸點出發，往西跨兩次
圖，站上圖 25 的 (12,31)——原版在那一格印「YOU HAVE REACHED THE BUCCANEER
BASE」。負對照：把量到的位移換成 (0,0)，同樣的預算連圖 26 都跨不過去。

## 邊界：三個方向各一張八支表

入口 0 在算下一步之前先過邊界檢查，每一支都是以 `DS:033Dh`（八方位索引，
0 起算：北、東北、東、東南、南、西南、西、西北）分派的 `ON GOTO`：

```
9914  COMPARE @4A9E, 255 ; IF = ; EXIT     ; 這個開起來就整支不跑
991C  COMPARE @49C4, 2  ; IF <= ; GOSUB 北緣
9927  COMPARE @49C3, 2  ; IF <= ; GOSUB 西緣     （25／26）
9932  COMPARE @49C3, 15 ; IF =  ; GOSUB 東緣
```

以 ecl6/25 為例，三張表分別是：

| 邊 | 位址 | 拒絕的方向 | 其餘 |
|---|---|---|---|
| 北（`49C4 <= 2`）| `9942h` | 0 北、1 東北、7 西北 | 放行 |
| 西（`49C3 <= 2`）| `9960h` | 5 西南、6 西、7 西北 | 放行 |
| 東（`49C3 == 15`）| `9985h` | — | 1 東北、2 東 → 跨到圖 26（`49C3 = 3`、`6E12 = 7`、`NEWECL 26`）；3 東南 → `49C4 == 31` 就拒絕，否則同樣跨圖 |

「拒絕」就是 `SAVE 255 → @6DC9`，也就是前端看到的「這一步不給走」。
26 與 27 的三張表形狀相同（`9964h`／`99B8h`／`9989h` 與 `9950h`／`99A3h`／
`9975h`），只是跨到的圖與新的 X 不同——這正是本規格前面那張跨圖表的來源，
補上的是**斜向也算**：帶北向分量的三個方向都會被北緣擋下，
帶西向分量的三個方向都會被西緣擋下。

## 可通行判定：原版也沒有

每一步的可通行判定：ecl7/26 `9A53h..9A90h` 用 `B019`（29 項）與 `B036`
（`DS:4AB3h >= 254` 時改用，20 項）比對 `DS:035Fh`，命中就
`SAVE 255 → DS:6DC9h`。

**`035Fh` 在原版沒有儲存**（spec 106）：ECL 的位址是虛擬的，`035Fh` 落在
「引擎暫存器」那一類，而取值函式（overlay-07 entry 15，`0E2Eh`）對它的
case **是空的**（`3d 5f 03 75 00`：比完就跳到下一個位元組），回傳的是一個
沒有初始化的堆疊區域變數。所以原版這道判定比的是堆疊剩下的東西，
remake 讓它一直是 0（不在任何一張表裡）——兩邊都沒有可靠的擋路行為，
**這一格不是 remake 少做了什麼**。實測隊伍可以一直往東走到 X 超過 15。

以下是找它的過程中排掉的，留著避免重跑：

- **不是 ECL。** 29 個區塊裡碰 `035Fh` 的只有三處，全是 `COMPARE`
  （ecl6/25 `9A0Eh`、ecl7/26 `9A77h`、ecl8/27 `9A33h`），沒有人寫。
- **不是 `9A36h` 的 `CALL @C01B`。** 那一條的選擇子算出來是
  `0xC01B − 0x7FFF = 0x401C`，而 `2Dh` 的分派器（overlay-03 `3026h`）
  只比 `AC91h`／`1`／`2`／`3A04h`／`401Fh`／`4019h` 六個值，其餘落到
  `3126h` 直接返回（spec 104 逐位元組核對過）。
- **絕對定址的搜尋看不到它**，但那不算證據：拿 `6DC9h`（ECL 明明會寫）
  當正對照，同一個掃描也是 0 命中。

掃不到是因為 **ECL 的位址是虛擬的**（spec 106）：直譯器先分類再決定去哪一塊
記憶體，位址是算出來的，不會出現 `mov [035Fh]` 這種形狀。引擎自己的固定槽
（`6E0Ch`、`6E4Ch`、`6A0Fh`）才是絕對定址，那些掃得到。

兩張表的內容（ecl7/26，值都小於 128）：

```
B019(29)  39 43 44 46 62 66 67 73 75 76 77 78 80 84 87 89 92 93 95
          99 104 105 106 110 111 116 117 118 119
B036(20)  39 43 44 46 67 73 75 76 77 78 80 84 99 105 106 119 87 22 6 10
```

前 16 項是主表的子集且順序相同，後面四項（87、22、6、10）不是。

**不是把座標壓成一個位元組。** 一個位元組放不下 14×26 個格子；而且拿同一
區塊的地點表當反例，三種最自然的壓法都會把走得到的地點壓成不可通行：

| 壓法 | 反例 |
|---|---|
| `X*16 + (Y−8)` | (6,16) → 104，在表裡 |
| `Y*4 + X/4` | (7,29) → 117，在表裡 |
| `(Y−8)*14 + (X−2)` | (6,16) → 116，在表裡 |

地點是走得到才有意義的，所以這三種都不成立。

**也不是同號 GEO 區塊的 terrain byte。** 三張野外 ECL 區塊各自有同號的
GEO 區塊，但它們的 terrain 值只有這些：

```
GEO6/25  0, 128..142
GEO7/26  0..5, 7..10, 128, 134
GEO8/27  128..145
```

低七位最多到 17，而表裡的值是 39..119——不論看原始位元組還是低七位都對不上。
進野外時真正載入的 GEO 是 **block 6**（ecl8/27 入口 4 的
`AC6Fh LOAD FILES 6, 6, 0` 加 `AC92h LOAD PIECES 17, 17, 17`），它的 terrain
值是 `0, 3, 4, 5, 6, 7, 9, 13, 74, 75, 128, 136, 140, 160, 192, 193, 194`，
同樣對不上。

**也不是牆的編號。** GEO 6／25／26／27 四張圖的牆值域都是 0..15。

**也不在 ECL 區塊裡。** 三張野外區塊的 payload 裡，位元組落在 32..127 的
最長連續段分別是 13、46、11 bytes（46 那一段就是這兩張表自己），
放不下 14×26 的地形格。

三張圖的表值域一致，交集也大——所以它是**跨圖共用的碼**，不是每張圖自己的
座標：

```
ecl6/25 @ADCE (8)   39 41 73 75 76 77 78 80
ecl8/27 @AB9E (8)   46 47 60 67 68 75 76 119
ecl7/26 @B019 (29)  39 43 44 46 62 66 67 73 75 76 77 78 80 84 87 89 92 93
                    95 99 104 105 106 110 111 116 117 118 119
```

三張表都**緊接在該圖的四張地點表之前**（`ADCE+8 == ADD6`、
`AB9E+8 == ABA6`、`B019+29 == B036`、`B036+20 == B04A`）。
