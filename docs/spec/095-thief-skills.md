# Spec 095：角色記錄的八個賊技能

狀態：READY（偏移、順序與數值由預設人物與規則書雙向釘住；基礎表與兩張修正表
在 `START.EXE` 裡的位置、原版建角實測值）；DRAFT（把三張表湊成實測值的公式）。
日期：2026-09-11。

## 位置與順序

記錄 `+77h` 起八個位元組，每個是百分比：

| 偏移 | 技能 |
|---|---|
| `+77h` | 掏包 |
| `+78h` | 開鎖 |
| `+79h` | 找／解陷阱 |
| `+7Ah` | 潛行 |
| `+7Bh` | 躲影 |
| `+7Ch` | 聽聲 |
| `+7Dh` | 爬牆 |
| `+7Eh` | 讀語言 |

## 怎麼釘住的

預設人物裡只有 `chrdatd4`（TINA，職業碼 6 ＝ 賊，賊等級 `+9Ch` ＝ 9）
這八格非零，其餘六名全是 0：

```
80 / 77 / 65 / 80 / 66 / 30 / 98 / 45
```

規則書第 9 級賊那一列是 `80 / 77 / 65 / 78 / 63 / 30 / 97 / 45`——
**五項到個位數相同**，另外三項高 1..3，是敏捷與種族修正。
兩個最有辨識度的值（爬牆接近 97、讀語言 45）都落在對的位置，
所以順序也一併定下來。

## 誰讀它

目前只有 `1Eh CHECKPARTY` 的 `6BA7h` 模式（spec 092），它統計整隊的
**找／解陷阱**（`+79h`）的最小值、最大值與平均——正是踩到陷阱之前該問的
那件事。

四種寫入版面在 38 顆 overlay 與 START.EXE 裡都掃過，**零命中**——但那個零
只證明「執行期間沒有人改它」，不證明建角時沒人算它。**建角時確實會算**，
見下一節。

## 原版建角真的會填它（dosgolem，2026-09-11）

拿 dosgolem 建兩個一級賊，寫出來的 `.CHA` 是

| 樣本 | 種族碼 `+2Eh` | 能力值 `+10h`..`+15h` | `+77h`..`+7Eh` |
|---|---:|---|---|
| 矮人賊 | 1 | `14 17 14 11 15 16` | `35 45 40 15 10 10 75 0` |
| 人類賊 | 7 | `16 17 15 13 14 14` | `35 35 25 15 10 10 85 0` |

兩個都是職業碼 `+2Fh` ＝ 6、賊等級 `+9Ch` ＝ 1。

**能力值的順序是 STR／INT／WIS／DEX／CON／CHA**——人物資料頁那一幕直接印著
（`docs/reference/original-dos/thief-sheet-dwarf.png`：`STR 14 INT 17 WIS 14
DEX 11 CON 15 CHA 16`，與記錄裡那六格一一對上）。所以矮人賊的 DEX 是 11、
人類賊是 13。

鍵序（`tools/dosgolem-reference.sh` 的 `POOL_DOSGOLEM_KEYS`）：

```
rep:9:Space,Return,Return,c,Return,Return,End,Return,Return,Return,
y,T,I,N,A,Return,k,e,y,a,a,e,rep:4:Return
```

職業選單那一層要多送一個 `End` 才會落在 `THIEF`——只按 `Return` 建出來的是
戰士（職業碼 2，八格全 0）。清單移動送 `End` 不是 `Down`（spec 133）。

## 兩張表在 `START.EXE` 裡

掃 AD&D 一級賊的基礎列 `30 25 20 15 10 10 85 0`，命中**檔案位移 `B424h`**
（DS 位址 `3C74h`，換算常數 `startDataSegmentFileDelta`）。往後每八格一列：

| 檔案位移 | 內容 |
|---|---|
| `B424h`..`B46Bh` | **基礎表**，第 1..9 級各八格 |
| `B46Ch` 起七列 | **種族修正**（第一列 `0 +10 +15 0 0 0 -10 -5` 的形狀正是矮人；接著的列對得上精靈、地精、半身人、半獸人與全 0 的人類）|
| `B4A4h` 起六列 | 還沒對上任何一個樣本。形狀像修正表（有負值），但**不是這裡用的**——見下一節 |

第 9 級基礎是 `70 62 60 70 56 30 98 45`，而 TINA（預設人物、9 級賊）是
`80 77 65 80 66 30 98 45`——差額要由上面兩張修正表補，所以三者是同一套。

## 種族修正表確認了，剩下一個 `+5 +10 +5` 沒有出處（DRAFT）

種族那七列與 AD&D 的表**逐格相同**，而且索引就是 `種族碼 − 1`：

| 列 | 種族（碼）| 內容 |
|---|---|---|
| `B46Ch` | 矮人（1）| `0 +10 +15 0 0 0 -10 -5` |
| `B474h` | 精靈（2）| `+5 -5 0 +5 +10 +5 0 0` |
| `B47Ch` | 地精（3）| `0 +5 +10 +5 +5 +10 -15 0` |
| `B484h` | 半精靈（4）| `+10 0 0 0 +5 0 0 0` |
| `B48Ch` | 半身人（5）| `+5 +5 +5 +10 +15 +5 -15 -5` |
| `B494h` | 半獸人（6）| `-5 +5 +5 0 0 +5 +5 -10` |
| `B49Ch` | 人類（7）| 全 0 |

**剩下的缺口很窄**：兩個樣本扣掉基礎與種族修正之後，差額都是

```
+5 +10 +5 0 0 0 0 0
```

**兩個樣本的差額一模一樣，而它們的 DEX 不同（11 與 13）、種族不同**，
所以那不是敏捷修正，也不是種族。矮人那一格的讀語言（基礎 0 ＋ 種族 −5）
在實測裡是 0，所以還有一道**下限夾到 0**。

實測值本身不在 `START.EXE` 裡（整列與前三格都掃過，零命中），所以是算出來的。

**不要再往下猜**：下一步是找**寫 `+77h` 那八格的程式碼**。先前「四種寫入版面
零命中」的掃描面對建角那條路可能有洞（`+77h` 是 disp8，八格連續也可能是
`rep movsb`），要換形狀重掃，並且先做正對照。再建幾個不同種族與職業的樣本
也能收窄——例如同種族不同 DEX 的兩個賊，可以直接判定敏捷到底有沒有參與。

## remake 現況

存檔的 `Character.ThiefSkills` 收這八格。remake 還沒有賊技能的產生端
（建角不寫、升級不寫），非賊本來就是 0，所以 `CHECKPARTY` 目前一律得到
0／0／0——**那是正確答案，不是佔位**。接上建角的賊技能之後這條就會動。
