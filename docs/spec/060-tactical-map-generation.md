# Spec 060：戰術地圖的生成

狀態：READY（配置大小、格位版面、標頭三個寫入、室內／室外的分岔與
`DS:495Bh` 的寫入、室外背景選擇、室外四支建構器與擲骰順序、室內生成的
視窗與迴圈順序、地城格到戰術格的投影與寫入規則、四支室內建構器的落筆樣式）；
未閉合（`08B4h` 沒命中的七個地形碼、`DS:35E2h` 的列數、地形旗標與牆面值
1／3 的玩家語意），逐條見〈未閉合〉。
日期：2026-09-25。

## 結論先講

戰術地圖**不是從資料檔載入的**，而是在戰鬥開始時生成。這解釋了為什麼
DAX 盤點裡找不到對應的 consumer——找不到不是儀器有洞，是原版真的沒有這種檔案。

生成的是**每格一個類別碼**；鋪在格子上的圖另有出處，見
[spec 131](131-combat-terrain-tiles.md)。

## 版面

`4E9h` ＝ 1257 ＝ 7 ＋ 50×25。前 7 個 byte 是標頭，其後是每格一個 byte 的
格位類別，列距 50——與 spec 057／058 由 `y×32h + x + 7` 反推的版面完全吻合，
而且是由配置大小獨立證實的。

配置後立刻寫下三個標頭 byte：

| 位移 | 值 | 已知用途 |
|---|---|---|
| +4 | 0 | 未定 |
| +5 | 1 | 未定 |
| +6 | 0 | 「跳過地形判定」旗標（spec 057）；0 表示判定生效 |

其餘四個 byte 在這一步沒有被寫。

## 室內還是室外：`12E5h` 與 `DS:495Bh`

`12E5h` 以 `DS:495Bh` 分岔兩次：`12EBh` 決定載哪一組圖塊（spec 131），
`136Bh` 決定跑哪一支生成器——等於 1 呼叫 `0820h`（室內），否則 `1255h`（室外）。

```
136b  80 3E 5B 49 01   cmp byte [495Bh], 1
1370  75 06            jnz 1378
1372  0E E8 AA F4      call 0820           ; 室內
1378  0E E8 D9 FE      call 1255           ; 室外
```

`DS:495Bh` 的寫入者全部掃過（所有 overlay 與 `START.EXE`，`mov byte [495Bh],imm`／
`mov [495Bh],al`／reg 三種定址）：overlay-03 四處、overlay-11 `03E6h` 一處（寫 1），
overlay-17 `1815h`／`1F4Eh` 只把它的位址載進 DI（`BF 5B 49`，用途未讀）。overlay-03 那四處都在主迴圈頂端
`3620h`（spec 025），**每一圈都重算**（exact）：

```
364d  A0 5B 49         mov al, [495Bh]
3650  A2 5A 49         mov [495Ah], al      ; 上一圈的值
3653  C6 06 5B 49 01   mov byte [495Bh], 1
3665  A0 A2 82         mov al, [82A2h]      ; 目前的 ECL 區塊
366a  3D 19 00 / 3D 1A 00 / 3D 1B 00        ; 25／26／27
3673  26 83 BD CC 01 00  cmp word es:[di+1CCh], 0   ; @49E6
367b  C6 06 5B 49 02   ; 區塊 25 → 2
3698  C6 06 5B 49 03   ; 區塊 26 → 3
36d6  C6 06 5B 49 04   ; 區塊 27 → 4
```

`[4933h]+1CCh` 是 ECL `@49E6`（class 0，spec 074）。野外三個區塊的腳本在走進地形時寫
0、進區域圖時寫 1（例：`ecl8/27 AC63h SAVE 0 @49E6` 接 `LOAD FILES 6,6,0`；
`AC86h SAVE 1 @49E6` 接 `LOAD FILES 27,2,255`）。所以**野外戰場的判準是「區塊
25..27 而且 `@49E6 == 0`」**，不看地圖名或座標；區域圖裡的戰鬥（`@49E6 == 1`）走室內。

remake：`gamepack.CombatAreaMode`、`cmd/pool-game/battlefield.go` 的
`combatAreaMode`／`generateTacticalGrid`。原版在主迴圈頂端算、戰鬥在同一圈之後才開，
remake 在開打當下取區塊與 `@49E6`；兩者只在同一圈裡 ECL 先改 `@49E6` 再開打時
才會不同（strong inference：沒找到這種腳本）。

## 室外：overlay-10 `1255h`

1. `FillChar(map + 7, 4E2h, 17h)`——整面 1250 格填成類別 `17h`（exact）。
   該類別在格位類別表裡的 `EntryThreshold` 是 1、`PathByte2` 是 0，
   也就是可進入、不擋路徑：平坦戰場。
   `17h` 同時是目的格探測（spec 058）寫下的初值，兩處是同一個常數。
2. 由 `[4933h]+186h`／`+188h` 取 X／Y——換回 ECL 位址就是 `@49C3`／`@49C4`，
   remake 的野外座標（exact：`6E00h + 49C3h×2 ≡ 186h`）。`495Bh` 為 3 時 X 加 `0Dh`，
   為 4 時加 `1Ah`（加在 byte 上，之後 `cbw`）。
3. 以 `y × 2Ch + x` 查 `DS:35E2h`，結果存進 `DS:45BCh`（exact）。表寬 44 寫死在
   `12A9h`；高 36 是 strong inference（第 34、35 列全是 `4Eh`，第 36 列起是
   `00 0D 1A`，正是三個模式的 X 偏移，已是下一份資料）。每張野外圖 13 欄，
   X 範圍 2..15。錨點：模式 4 的 (9,29)（東邊登陸點）查到 `ECh`。
4. 依序呼叫 `0C7Ah`、`0DB0h`、`0F3Fh`、`0000h`（exact）。

### 地形旗標：`08B4h`

讀 `DS:45BCh`，照 24 條區間比對回一個旗標 byte，**先命中先算**（後面與前面重疊的
區間輪不到，例如 3..4 同時在第 4、5 條）。完整比對表逐條抄在
`internal/combat/outdoormap.go` 的 `outdoorFlagRules`，每條註解原始位址。
比對完之後（`0C02h..0C21h`）：旗標帶 80h 而且 `[4933h]+366h`（ECL `@4AB3`）等於
`FFh` 時，旗標改成「去 80h、或上 1」。`@4AB3` 也是市政廳公告表第 13 筆的旗標
（spec 041，斯托約諾河那一則）。

四支建構器各自讀的位元（exact）：

| 位元 | `0C7Ah` | `0DB0h` 密度 | `0F3Fh` 權重 |
|---|---|---|---|
| 01h | — | — | — |
| 02h | — | 1 | c=2Dh、d=0Ah |
| 04h | — | 3 | c=19h |
| 08h | — | 7 | — |
| 10h | 門檻 4Bh | — | — |
| 20h | 門檻 23h | — | — |
| 40h | — | 4，並重擲高度 | d=5、e=1Eh；1d4 的 4 不重擲 |
| 80h | — | 0 | a=0Fh、d=19h、c=0Ah |

同一支裡後檢查的位元蓋過先檢查的（表的順序就是檢查順序）。位元的玩家語意
（河、林、岩……）沒有讀到文字證據，程式裡只用位元值命名。

### 四支建構器

共同規則（exact）：

- 都直接寫 `[6674h] + 7 + y×32h + x`，**不經過** `022Eh` 的加一，寫下的就是存進地圖的類別。
- 落筆前檢查 `[類別×4 + 275Bh] == 16h`：275Bh 是類別表 `DS:2758h` 每筆的第四個 byte
  （`PresentationCode`）。序號 16h 的類別只有 `17h` 與 `36h`，也就是「還是平地」。
  所以後跑的建構器不會蓋掉先跑的。
- 擲骰都是 `0100h:0048h`（overlay-24 entry 8，`Roll(count, sides)`），每顆骰是
  `System.Random(sides) + 1`（`5BBh:0C94h`），加總存成 byte。
- 迴圈外層 X 0..49、內層 Y（`0DB0h` 從 1 開始，其餘從 0）。寫入不檢查列尾：
  `0C7Ah` 在 x = 49 那一列的右半格照平面位移落到下一列的 x = 0（起點 26 時的第 23 列）。

| 建構器 | 做什麼 | 擲骰順序 |
|---|---|---|
| `0C7Ah` 斜帶 | 1d100 大於門檻（預設 0）就不畫。起點 x₀ = 34 − 5d4，往左退到 (x₀+2) 是 7 的倍數（12、19、26）。每一列 y 在 (x₀+y, y) 寫 `32h`、右一格 `33h`；那一列 1d20 擲 1 或計數是奇數時改寫 `34h`／`35h`（`0C31h`，計數加一），所以交叉總是連兩列。X 超過 49 的列不畫也不擲。整條沒交叉就在 y = 16 − 1d9 補兩列交叉。 | 1d100；5d4；每個畫到的列 1d20；最後可能 1d9 |
| `0DB0h` 直立物 | (x,y) 與 (x,y−1) 都是平地時擲 1d100，≤ 密度才放。高度 v：1d10 > 8 時 1d2+4，否則 (v+1)/2；旗標 40h 再以 1d3+3 取代。下半 (x,y) 寫 `v+23h`，v < 5 時上半 (x,y−1) 寫 `v+1Fh`。 | 每對平地 1d100；中了再 1d10（可能 1d2）、40h 時 1d3 |
| `0F3Fh` 撒點 | 每格平地擲 1d255，依預設權重 a=0、b=6、c=0Fh、d=28h、e=0（旗標改寫見上表）累加分支：≤a → 1d4，4 且上一格平地時上 `41h` 下 `40h`，1..3 寫 `v+3Ch`；≤a+b → `1d3+36h`；≤a+b+c → `1d4+29h`；≤a+b+c+e → `(1d10−1)/3+1+38h`；≤a+b+c+e+d → 1d4（4 且沒有 40h 時改 1d3）`+2Dh`；其餘不放。 | 每格平地 1d255，中了再一到兩顆 |
| `0000h` 隨機物件 | 每格平地 1d100：98 → `1Ah`，99 → `1Bh`，100 且區塊 `DS:82A2h` 不是 0Ah 時再擲 1d100，擲 1 才以 1d10 放 `1Ch`（1..6）或 `1Dh`（7..10）。 | 每格平地 1d100；少數再 1d100、1d10 |

寫下的類別全落在 `1Ah..1Dh`（序號 22h..25h，RANDCOM）與 `20h..41h`（序號
00h..21h，WILDCOM）。

### 未閉合

1. **`08B4h` 沒命中的地形碼。** 野外三張圖可走的格子裡有七個碼（86h、BBh、F9h、
   FBh、FDh、FEh、FFh）一條都不中，原版回的是區域變數 `[bp−2]` 的殘值——取決於
   前一個用到同一個堆疊位置的常式，靜態讀不出來。remake 用
   `OutdoorUnmatchedFlags = 0`（hypothesis，明確標示的退路）。
   `TestEveryReachableWildernessTerrainHasFlags` 把這七個碼釘住。
   閉合要在 dosgolem 站在這種格子上開打、讀 `[6674h]`。
2. **`DS:35E2h` 的列數**：36 是 strong inference，見上面第 3 步。
3. **旗標與類別的玩家語意**：只知道哪一支建構器怎麼用它、畫出來是哪一張圖塊。
4. **亂數流不同**：remake 的骰子不是 Turbo Pascal 的 `RandSeed`（`DS:438Ah`），同狀態下
   盤面不會逐格相同；規則與擲骰順序照原版。原版對照見下一節。
5. **生成之後還有別的寫入者。** 原版戰場有一格類別 `1Fh`（序號 27h，RANDCOM
   item 5）不是 `1255h` 寫得出來的。候選指令 `26 C6 45 07 1F` 在 overlay-10 `1DDBh`、
   overlay-12 `0E5Ch`、overlay-32 `0FB9h`，都沒讀；remake 沒有寫它。

### 原版對照（dosgolem，2026-09-25）

收據 `docs/audit/dosgolem-outdoor-battlefield.json`：dosgolem `57454c4`、`START.EXE`
`12811cbc…810d9f`，從作弊通關留下的 `ending-wild.state`（野外 27 登陸點）按 13 個鍵
走到隨機遭遇、選 COMBAT，開打後讀 `DS:495Bh`、`DS:45BCh`、`[6674h]` 的 4E9h bytes，
以及按下 COMBAT 之前的 `RandSeed`。

- 登陸點 `@49E6 = 0`、`495Bh = 4`；開打時 `(49C3, 49C4) = (8,29)`、`45BCh = EAh`，
  與 `Background(4, 8, 29)` 相同（exact）。標頭 `+4..+6 = 00 01 00`。
- `System.Random`（`5BBh:0C94h`）是 `RandSeed = RandSeed × 08088405h + 1`、
  回傳新種子高 16 位 mod n（bytes exact）。從按鍵前的種子往前推 5 次再跑
  `GenerateOutdoorTacticalGrid`，**1250 格有 1249 格與原版相同**；唯一不同的就是上面
  第 5 條那一格。這把背景選擇、`08B4h` 的旗標（`EAh → A0h`）、四支建構器的規則與
  每一次擲骰的順序一起釘成 exact。`TestOutdoorGeneratorReproducesTheDOSBattlefield`
  每次重跑這個比對。
- 這一場旗標是 A0h（20h＋80h）：帶狀那一擲沒中、直立物密度 0，所以盤面只有撒點與
  隨機物件；`0C7Ah`、`0DB0h` 的落筆由單元測試逐分支釘住，還沒有原版收據。

## 室內：overlay-10 `0820h`

由地城幾何生成，不是填平面：

外層 `dy` 由 −2 到 +2、內層 `dx` 由 −6 到 +6，共 13×5 ＝ 65 個地城格。
每一格以隊伍座標（`DS:6A0Bh`、`DS:6A0Ch`）加上偏移得到地城座標，
再用三次牆面查詢（`01BAh`，方向碼 6、0、2）取得該格三個方向的牆，
最後交給四支建構器 `02BEh`、`037Bh`、`0413h`、`061Fh` 寫進戰術格。

### 牆面查詢

`01BAh` 是雙向的：先問這一格朝 `dir` 有沒有牆，再問鄰格朝 `(dir+4) mod 8`
有沒有牆，兩者取 OR。方向碼沿用 spec 056 的方向環，`+4` 就是反向。
`0820h` 對每個地城格用方向 6、0、2 各問一次，結果留在區域變數裡供建構器讀。

單側的查詢在 `0138h`，它把 GEO 資料換成 0／1／3：

1. 座標超出 16×16 時一律回 1（牆），只有「`y` 等於隊伍的 `DS:6A0Ch`、
   且方向是 2 或 6」例外，回 0。走廊因此可以延伸出盤面。
2. 界內先問 overlay-30 entry 5；回 0 就是 1（不可通行）。
3. 可通行時再問 overlay-30 entry 4；回 0 就是 0（開放），非 0 就是 3。

以 GEO 資料表達即：沒有牆是 0，有牆且該方向的 detail 位元為 0 是 1，
有牆且 detail 非 0 是 3。《青色枷的詛咒》已完成的 remake 也是這三個結果
（`dungeonOneDirection`），只是它的第一個判斷寫成「有沒有牆」而不是
「可不可通行」，措辭相反、產出相同。

### 投影：`022Eh`

戰術格的座標由地城格與格內細部位移算出：

```
X = 21 + 6×dx + 5×dy + subB
Y = 10 +        5×dy + subA
```

**X 也吃 dy 的位移，所以整張圖是斜的**，不是把地城格正交排成方塊。
同一條式子在《青色枷的詛咒》已完成的 remake 裡也是這樣寫的
（`internal/mapdata/dungeon.go` 的 `column*6 + row*5 + 21 + x`、
`row*5 + 10 + y`），那是同一族引擎的獨立實作，與本規格的讀法一致；
該實作同樣以 `0x16` 當地板、以牆面值 `== 1` 判牆。
算完之後才檢查 `0 ≤ X ≤ 49`、`0 ≤ Y ≤ 24`，超界就整格不寫——
視窗的四個角本來就落在盤面外，原版靠這個檢查裁掉，而不是先縮小視窗。

寫入的值是**建構器傳入的類別加一**。建構器用的是 0-based 編號，
加一之後正好對上格位類別表折疊過的 1-based 索引（spec 057）。
第一支建構器 `02BEh` 以類別 `16h` 鋪地板，加一之後是 `17h`——
與室外整面填的類別是同一個。

### 四支建構器

牆面值只有 0、1、3 三種。四支建構器各自負責地城格內不重疊的一塊：

| 建構器 | 位址 | 範圍（subA, subB） | 依據 |
|---|---|---|---|
| 西帶 | `02BEh` | subA 2..4、subB 0..5 | 西牆 |
| 北帶 | `037Bh` | subA 0..1、subB 3..4 | 北牆 |
| 西北角 | `0413h` | subA 0..1、subB 1..2 | 北牆、西牆、角落是否通透 |
| 東北角 | `061Fh` | subA 0..1、subB 5..6 | 北牆、東牆、上一格的東牆、右一格的北牆 |

西帶先把 18 格鋪成地板，再依西牆值畫上去。西牆為 1 時畫的是一條**斜線**
（每一列的牆格跟著 subA 往右挪一格），因為投影本身是斜的；西牆為 3 時
只動兩格。北帶只分「等於 1」與「其他」——值 3 走的是地板那一支。

兩個角落建構器是自動接圖表：各以四個條件選出 2×2 的四個類別。
西北角的「通透」由上一格的西牆與左一格的北牆都不存在決定；
東北角則看上一格的東牆與右一格的北牆。完整分支見
`internal/combat/indoormap.go`，每一支都有逐分支的測試釘住。

牆面值 1 與 3 的玩家語意（實牆與門之類）尚未閉合，因此程式裡不給它們
具象名稱。

## 生命週期

overlay-08 的 unit 初始化（`0000h`）其實是拆除：先走訪 `DS:6CAFh` 的串列
逐節點釋放 `13h` bytes，再釋放 `DS:6674h` 的 `4E9h` bytes 並把指標清零。
因此戰術地圖的存活期是一場戰鬥，不跨戰鬥保留。

## READY 契約

1. 戰術地圖在戰鬥開始時生成，不得改成從檔案載入或預先烘焙進 game pack。
2. 格數固定 50×25，標頭 7 bytes；配置大小 `4E9h` 是這個版面的獨立佐證，
   兩者不一致時以原版位元組為準。
3. 室外戰場先整面填類別 `17h`，再依序跑 `0C7Ah`、`0DB0h`、`0F3Fh`、`0000h`；
   不得跳過標頭 `+6` 的寫入，也不得改變建構器順序或擲骰順序。
   是否室外只看 `DS:495Bh`（區塊 25..27 且 `@49E6 == 0`），不看地圖名或座標。
4. 室內戰場的生成順序是外層 Y、內層 X，兩層都由負值遞增。
5. 投影照 `X = 21 + 6dx + 5dy + subB`、`Y = 10 + 5dy + subA` 原樣實作；
   不得改成正交排列，也不得先裁視窗再算——超界的判定要發生在算完之後。
6. 寫入地圖的類別是建構器類別加一；不得把加一併進建構器的常數裡，
   那會讓表的 1-based 折疊在兩處各留一半。
7. 四支建構器的落筆區域不重疊，順序是西帶、北帶、西北角、東北角；
   西帶先鋪地板再畫牆，這個順序不能倒過來。
8. 牆面值只接受 0、1、3；其他值在原版會讓區域變數維持未初始化，
   重建時一律失敗即關閉，不得自行補預設。
9. 室外建構器直接寫類別、不加一；落筆條件是「該格的 `PresentationCode` 為 16h」。
10. 室外戰場的圖塊取 WILDCOM，室內取 DUNGCOM，序號 22h 起兩邊都取 RANDCOM（spec 131）；
    部署在室外不查牆（spec 061）。
