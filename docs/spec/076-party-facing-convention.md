# Spec 076：隊伍朝向的座標系

狀態：CONFORMED（Pool 的朝向是 0..3，0 北、1 東、2 南、3 西；共用 engine 的
牆面查詢用 0/2/4/6，兩者要在 Pool 這一側換算）。日期：2026-09-03。

## 原版只用 0..3

開場事件的出生點加上 34 步導覽，共 35 個位置，朝向欄只出現 **0、1、2、3**
（各 3、1、9、22 次）。4..7 一次都沒有。

方向的對應由導覽自己證明：Gold Box 的導覽是一步一步往前走，所以每一步的
位移應該等於**上一步的朝向**。用 `0=(0,-1) 1=(+1,0) 2=(0,+1) 3=(-1,0)`
去對 34 步裡有位移的那 20 步：

| 相符 | 不符 | 原地不動 |
|---:|---:|---:|
| 20 | 0 | 14 |

零例外。這是可以被推翻的預測——換成別的對應（例如 0 北 1 西）馬上會出現不符
——所以 `0 北 1 東 2 南 3 西` 是 **exact**。

## 共用 engine 用的是另一套

`geometry.WallWrapped` 與 `CanMoveDungeonWrapped` 只認 0、2、4、6，其餘一律
回 false。兩套系統相差一個 2 倍，所以 **Pool 這一側要在呼叫邊界乘 2**：
`Spawn.Direction()` 就是這個換算。engine 不動——它服務兩個作品，改它會動到
《青色枷的詛咒》。

## 混用造成的三個症狀

- **隊伍走不動。** 導覽在 `(0,4)` 結束時朝向 3。前進的程式只接受 0/2/4/6，
  轉向又是 45 度一步，從奇數朝向永遠轉不到偶數——按任何鍵都得到
  「Face a cardinal direction before moving forward」。開場結束之後隊伍
  卡死在原地，主線第一步就走不出去。
- **牆面查詢靜默回空。** 開場流程拿朝向直接呼叫 `WallWrapped`；朝向 1 或 3
  時它回 `(0, false)`，也就是「這個方向沒有牆」。35 個位置裡有 23 個是奇數
  朝向，**三分之二的導覽步驟一直在對著一個假的答案跑**，而且沒有任何錯誤
  訊息。
- **存檔驗證把合法值判成非法。** `validateCampaign` 要求朝向是偶數且不大於
  6，正好把原版真正會出現的 1 與 3 擋掉。

## 換算之後

- 轉向改成 90 度一步（`(facing + 1) % 4` 與 `(facing + 3) % 4`），
  四個朝向都走得到。
- 前進的位移直接用 `0 北 1 東 2 南 3 西`。
- 呼叫 engine 的牆面、移動、第一人稱視野一律傳 `Direction()`。
- 存檔驗證改成 `朝向 ≤ 3`；schema 6 以前存的是乘過 2 的值，載入時除以 2。

`DOSInitialSpawn()` 原本寫 `Facing: 6`，那是同一個位置 `(15,1)` 的朝向 3 被
乘過 2 的結果，現已改回 3——它與開場事件讀出來的出生點是同一筆資料。
