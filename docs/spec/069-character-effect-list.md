# Spec 069：角色的效果串列（`.spc`）

狀態：CONFORMED（檔案形狀、節點版面、與已裝備魔法物品的對應、十五個代碼的
顯示名稱）；DRAFT（節點 `+1`..`+4` 的語意、效果如何影響數值）。
日期：2026-09-03。

## 它不是記憶的法術

原版的預設人物檔是三個一組：`.sav`（285 bytes，角色記錄）、`.itm`
（63 的倍數，物品記錄）、`.spc`（9 的倍數）。`.spc` 看起來像「記住的法術」，
但**持有它的人包括一名 8 級戰士（HAPLO）與一名 9 級賊（TINA）**，
那個讀法說不通。

## 原版只有這一份（2026-09-11）

戰鬥中掛效果不會另開一條串列：overlay-24 entry 10（`0E54h`）是
`GetMem(9)` 接在**角色記錄 `+7Fh`** 串列的尾端（spec 112 的表）。所以

- 隊員在戰鬥中中的詛咒，戰鬥結束後**本來就還在**——沒有「寫回」這個步驟；
- 怪物的效果掛在怪物記錄上，記錄隨戰鬥消失，效果也就跟著沒了。

remake 這一側目前是兩份（戰術盤面一份完整節點、存檔一份只有效果碼），
兩個方向都還沒接：進戰鬥沒帶入、出戰鬥沒寫回。細節與卡點見 worklist 的
`combat-effects-not-persisted`。

## 持續 `0` 是「不會被取代」（2026-09-11）

先回答一個常見的猜法：**原版不是用位元表示狀態**。存檔的 `.spc` 就是這條串列
本身，9 bytes 一個節點原樣寫出去（連那個重新載入後沒有意義的遠指標都存著），
不是一個狀態位元組。remake 存檔那側的 `Effects []uint8` 只留效果碼，比原版少
掉持續與等級。

節點 `+1..+2` 的來源確定了：overlay-24 entry 10（`0E54h`）掛節點時
`ax = [bp+0Ah]` 寫進 `es:[di+1]`，正是簽章裡的「持續」（spec 112）。

**而 `0` 在那個欄位是特殊值**，overlay-24 `16D3h` 那一段：

```
16D3  cmp WORD PTR es:[di+1], 0    ; 舊節點的持續是 0 嗎
16D8  jbe 16E6
16DA  ax = [bp+12h]                ; 新效果的持續
16E0  cmp ax, es:[di+1]
16E4  ja  16EC                     ; 新的比較久 → 摘掉舊的
16E6  cmp WORD PTR [bp+12h], 0     ; 新的持續是 0 嗎
16EA  jne 1700                     ; 不是 → **不摘**，舊的留著
16EC  call 0028h                   ; 摘節點
```

舊節點持續為 0 時，任何有限持續的新效果都取代不了它，只有另一個 0 可以。
「永久到治好為止」要的正是這個行為。

**但遞減點還沒找到，而且不能說它不存在。** 掃「對節點 `+1` 做 word 遞減」
在 38 顆 overlay 全部零命中——**那個零不算數**：正對照顯示連
`dec WORD PTR` 這個形式在整包裡都是 0 筆，Borland 產的是「載入暫存器、遞減、
寫回」，所以我的 pattern 從一開始就抓不到目標。要重掃得換成「讀 `es:[?+1]`
到暫存器之後接 `dec`」的形狀，並且一樣要先做正對照。

在那之前，**不要把「持續會不會倒數」當成已知**——它同時相容於兩個世界：
`+1` 是剩餘回合數（會倒數），或是強度／施法者等級（不倒數，只比大小）。
spec 121 記的臭雲術實參是「持續＝施法者等級」，兩種讀法都說得通。

## 它是 spec 059 的效果串列

節點的形狀不是從檔案猜的，有兩個獨立來源：

1. overlay-25 entry 27 走訪串列時，節點的 `+0` 是效果代碼、`+5` 是下一個
   節點的遠指標（spec 059）。
2. overlay-24 `0E54h` 掛新效果時 **`mov ax, 9` 之後呼叫配置常式**
   （`docs/audit/ida-overlay24-effect-append.json`）——節點就是 9 bytes，
   不是從 `.spc` 的檔案大小回推的。

9 bytes 正好是 5 bytes 內容加 4 bytes 遠指標。

結構上的佐證：兩節點的檔案（`chrdatd3.spc`、`chrdatd4.spc`）裡，
**第一個節點的遠指標非零、最後一個是零**。讀法若錯位，這個規律不會成立。
存進檔案的指標是上次執行時的位址，重新載入沒有意義；走訪照檔案順序，
不追指標。

## 代碼與已裝備的魔法物品一一對應

掃過全部 20 個預設人物：

| 代碼 | 只出現在 | 樣本數 | 反例 |
|---|---|---:|---:|
| `3Dh` | 戴著 Ring of Fire Resistance（物品型別 `45h`）的角色 | 4 | 0 |
| `26h` | 戴著 Gauntlets of Ogre Power（型別 `3Fh`）的角色 | 3 | 0 |

一對一、沒有反例，橫跨戰士、牧師與賊。

**`3Dh` 已由原版的字串證實**：overlay-15 `0F9Ch..12FFh` 那串
`cmp ax, 碼` 的顯示名稱鏈裡，`3Dh` 字面上就叫 "Fire Resistance"
（見下一節）。`26h` 不在那串鏈裡——Gauntlets of Ogre Power 改的是力量，
顯示在能力值上，不掛具名狀態，所以那一條仍是 `strong inference`。

## 掛上與拿掉

**掛上**（overlay-24 `0E54h`）：配置 9 bytes，串列是空的就當頭，
否則**走到尾端接上去**。`.spc` 的節點順序因此就是掛上的先後。

**拿掉**（overlay-24 `0028h`，`docs/audit/ida-overlay24-effect-remove.json`）：
以效果代碼從頭線性搜尋；找到之後先看節點的 `+4`（一個旗標，語意未閉合），
再依「它是不是頭」分兩條路解開連結。

## 誰在掛效果

掛效果的助手是 overlay-24 entry 10。它的 TPOV stub 可以從清冊算出來，
不必反組譯：entry 的 `executable_file_offset` 減 `stub_offset` 得到控制記錄的
檔案位移，再減 MZ header（`3B0h`）除以 16 就是 runtime segment。
本例是 `0100h:0052h`，因此呼叫端的位元組是 `9A 52 00 00 01`。

（IDA 以平坦 16-bit 載入 overlay 時會把這個遠指標解成 overlay 內的
`sub_1052`——`0100h:0052h` 在平坦位址剛好是 `1052h`。那是載入方式造成的
巧合，不是真的呼叫同一顆 overlay 裡的函式。）

用這個位元組去掃，掛效果的呼叫端有三處：

| overlay | 次數 | 已知身分 |
|---|---:|---|
| 12 | 多處 | 效果產生器（既有 `ida-overlay12-*` 匯出）|
| 16 | 多處 | 建角與衍生數值 |
| 22 | 5 處（`1344h`、`18E5h`、`1BD1h`、`202Eh`、`2EF9h`）| 法術 overlay |

overlay-22 那五處就是效果被掛上去的地方。`1344h` 那一處在函式 `120Eh`
裡（`docs/audit/ida-overlay22-effect-attach-site.json`）：它先以
`ds:6779h` 與常數 `0Ch` 呼叫 overlay-22 內的 `07C7h`，再把算出來的值連同
記錄傳給掛效果的助手。

`07C7h`（`docs/audit/ida-overlay22-effect-magnitude.json`）是**效果數值的
擲骰器**：拿 `ds:6779h` 逐值比對，各自擲一組骰子並套一個換算，例如

| `ds:6779h` | 回傳 |
|---|---|
| `28h` | `roll(1,6) × 10` |
| `39h`／`3Dh` | `roll(5,4)` |
| `3Bh` | `roll(1,4) × 10 + 40` |
| `3Fh` | 依 `ds:4954h` 分支，`roll(2,10)`… |

⚠ 那些比對值**落在物品型別的範圍**（`3Bh` 盾、`3Dh` 法師卷軸、`3Fh` 力量護手），
不是法術編號（法術只到 `38h`）。所以 `ds:6779h` 比較像「正在使用的物品型別」，
`120Eh` 因此可能是**用物品**而不是施法的路徑——overlay-22 同時管
`Cast`／`Memorize`／`Scribe`／`Learn`，卷軸也在它手上。**這一點還沒定**，
在讀到 `ds:6779h` 的寫入端之前不下結論。

確定的是形狀：效果節點的數值是這樣擲出來的，掛上去的是「記錄 ＋ 一個擲骰
結果 ＋ 另一個 byte」。

## 代碼 `59h` ＝ Displaced

原版的名稱鏈把 `59h` 叫 "Displaced"，對應的裝備是 Cloak of Displacement。

**但持有它不等於掛著它**：TARRY（`chrdatd5`）身上有一件 Cloak of Displacement
卻沒有 `59h`，而兩個 CARRY（`chrdatd6`、`chrdate6`）有 `59h`。
所以這個代碼跟的是「裝備中」而不是「持有」，與 `3Dh`／`26h` 那兩條
（比對的就是**裝備中**的魔法物品）同一套。這一點還沒讀到寫入串列的程式碼，
標 `strong inference`。

節點內容也還沒閉合：`3Dh` 的四個 byte 是 `00 00 0C 00`，`59h` 在兩個 CARRY 上
分別是 `00 00 0C 00` 與 `00 00 1C 00`。差異與等級（6 與 5）對不上明顯的關係。

## 為什麼先做這一段

效果串列是法術與魔法物品**共用**的落點：法術施展之後要把效果掛上去，
魔法物品裝上去也要。先把容器的形狀釘住，之後兩邊都不必各自重猜一次。

## 不做

- 不替 `3Dh`／`26h` 取名成「抗火」「巨人之力」。相關性成立不等於語意成立，
  而取了名之後別人會當成已證實。
- 不猜 `59h`，也不猜節點內容的四個 byte。
- 不把效果接進數值計算。要接得先讀寫入串列的那段程式碼。
