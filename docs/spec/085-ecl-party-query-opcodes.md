# Spec 085：三條對隊伍發問的 opcode（`32h`、`22h`、`23h`）

狀態：READY（三條的判定與寫回位址都讀完並實作）。日期：2026-09-03。

三條的共同形狀：讀隊伍或擲骰算出一個值，寫進 ECL 變數，不需要任何畫面。

## `32h FIND ITEM`（overlay-03 `2847h`，1 個運算元）

```
2864h  把 DS:6D3Eh 起六個位元組清成 0
2875h  [6D3Fh] = 1                       ; 預設「沒找到」
287Ah  char = [5CF4h]                    ; 隊伍鏈，+104h 是下一個
28A4h    item = char.[+C8h]              ; 物品鏈，+2Ah 是下一件
28B2h      item.[+2Eh] == 運算元 1 時：
             [6D3Eh] = 1；[6D3Fh] = 0；停止整個搜尋
```

比的是**物品型別索引**（`+2Eh`），不是名字，也不看穿戴中與否。
找到就整個停下來，不會繼續掃後面的人。

## `22h PARTY SURPRISE`（overlay-03 `16FCh`，2 個運算元）

走隊伍鏈，任何一個人的職業碼（`+2Fh`）是 **4 或 0Ah** 就把運算元 1 指到的
變數設成 1，否則 0；**運算元 2 一律寫 0**（第二個累加器從頭到尾沒被寫過）。

職業碼由七名預設人物釘住：三名戰士 2、牧師 0、兩名法師 5、賊 6，
與 spec 075 的職業槽編號同一套。**《光芒之池》的建角表沒有 4 與 0Ah**
（那是遊俠與牧師／遊俠），所以自己建的隊伍一律得到 0——那是正確結果，
不是還沒接；那兩個碼只會由 `36h ADD NPC` 帶進來。

## `23h SURPRISE`（overlay-03 `1798h`，4 個運算元）

```
17CEh  隊伍門檻 = 運算元 4 + 2 − 運算元 1
17E2h  對方門檻 = 運算元 2 + 2 − 運算元 3
17F6h  兩次 骰(1, 6)
1812h  隊伍骰 ≤ 隊伍門檻 → 結果 = 1
183Ah  對方骰 ≤ 對方門檻 → 結果 = 2
184Dh  [6DCBh] = 結果
```

兩個門檻的配對（4 減 1、2 減 3）是原版的樣子。

**結果碼 3 到不了**：`1830h` 在「兩邊都沒過」時寫下 3，然後直接落進
`183Ah`，而那一段在同一個條件下會把它改成 2。實作照抄——原版把「兩邊都被
突襲」當成「對方被突襲」處理，改成看起來合理的版本就不是原版了。

## remake 怎麼接

三條都走 passthrough。`32h` 與 `23h` 寫的是固定位址（`6D3Eh`／`6D3Fh`、
`6DCBh`），`22h` 寫的是運算元自己帶的位址——那要用 `WordAddress`，
用 `NumericValue` 會把變數的**內容**當成位址。

## 還沒讀

- `6D3Eh` 起被清掉的另外四個位元組給誰用。
- `+2Fh` 的完整職業碼表（本作用得到的六個已由預設人物釘住）。
