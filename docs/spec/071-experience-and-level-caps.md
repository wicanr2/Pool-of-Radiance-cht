# Spec 071：經驗值門檻表與等級上限

狀態：CONFORMED（表的位址與版面、四個職業的門檻、上限哨兵、昇級常式讀寫的
三個欄位）；DRAFT（昇級時 HP／THAC0 的重算細節、可記憶法術數）。
日期：2026-09-03。

## 昇級常式

overlay-22 `2C6Bh..2D8Fh`（`docs/audit/ida-overlay22-level-up.json`）逐個職業
索引 0..7 走一遍，對每個有等級的職業比較經驗值與門檻：

```
2C89  add di, ax               ; di = record + class
2C8B  mov al, es:[di+96h]      ; 那個職業目前的等級
2CB7  mov dx, 38h              ; 56 ＝ 一個職業的列長
2CBA  mul dx
2CC0  cmp word ptr [di+4015h], 0   ; 門檻的高位字
2CE9  les ax, [di+4013h]           ; 門檻（32 bit）
2D51  inc byte ptr es:[di+96h]     ; 升一級
2D74  mov es:[di+0ACh], ax         ; 記下一級的門檻
```

取值方式是 `class × 38h + (level+1) × 4 + 4013h`，所以表是
**8 個職業 × 14 個 4-byte 欄位**；欄位索引 k 是「升到第 k 級所需的經驗值」，
第 0、1 欄不用。

昇級前那幾行同時改了 `+32h`（最大 HP）、`+11Bh`（目前 HP）、`+0B1h`、
`+75h`、`+74h`——HP 的重算細節本規格不涵蓋。

## 門檻與 AD&D 逐項相同

| 職業索引 | 職業 | 升到 2..N 級的門檻 |
|---:|---|---|
| 0 | 牧師 | 1501, 3001, 6001, 13001, 27501 |
| 2 | 戰士 | 2001, 4001, 8001, 18001, 35001, 70001, 125001 |
| 5 | 法師 | 2501, 5001, 10001, 22501, 40001 |
| 6 | 賊 | 1251, 2501, 5001, 10001, 20001, 42501, 70001, 110001 |

## 上限是哨兵讀出來的

`FFFFFFFF` 表示那一級到不了——它不是一個很大的門檻，程式也不是這樣用的
（`cmp word ptr [di+4015h], 0` 先看高位字，負值直接跳過）。因此上限直接讀得出來：
**牧師 6、戰士 8、法師 6、賊 9**，與《光芒之池》公認的等級上限相同。

## 索引 1／3／4／7 沒有進程

那四列一整列都是哨兵。spec 063 說在原版證據命名之前不得替它們取名；
本規格只記錄事實，不推論它們是什麼。

## 可記憶法術數（已由 spec 072 解出）

本規格當初沒找到的那張表在 overlay-23，位址是 `DS:4035h`（牧師）與
`DS:414Dh`（法師）。以下保留當時的搜尋紀錄，因為失敗的原因本身有用。

### 當時的搜尋

原本要找的是「每級可記憶幾個法術」。AD&D 的進程（法師 1/2/2/3/4/4…、
牧師 1/2/2/3/3/3…）以列優先、行優先、補零到 4 或 5 欄、加 1-based 前綴
等六種版面在 START.EXE 與全部 38 顆 overlay 裡都找不到（正對照：同樣的搜尋
在職業 THAC0 表上一次就命中）。

**它很可能是用比較鏈算的，不是查表**——spec 065 的三個能力值修正就是這樣寫的。
從原版資料反推得到的兩個點與 AD&D 一致：CARRY（法師 6）記了 4/2/2，
ALFRED（牧師 6、睿智 18）記了 5/5/3 ＝ 基礎 3/3/2 加睿智加成 2/2/1。
兩個點還不足以定表，因此不寫進程式碼。

## 不做

- 不從 AD&D 規則書補可記憶法術數。兩個資料點不是一張表。
- 不替索引 1／3／4／7 取名。
- 不接昇級流程本身。門檻有了，HP 與 THAC0 的重算還沒讀完。
