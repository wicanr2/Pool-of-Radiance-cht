## 敵方回合長什麼樣子

一隻怪物的一個回合由 overlay-09 的三支撐起來：

| 位置 | 角色 |
|---|---|
| entry 1（`000Fh`） | 分派：玩家打斷 → 戰術模式擲骰 → 士氣 → 用物品 → 轉變不死生物 |
| entry 5（`0B3Ch`） | 接近迴圈：搆得到就打，搆不到就走一步，最多二十輪 |
| entry 13（`07E8h`） | 一步：算基準方向，照戰術模式的五個相對偏移依序試 |

**選路的判準是「進不進得去」，不是「離目標多近」**：五個相對方向依序問，
第一個地形走得過去又沒人佔著的就走，不比較距離。走不成的時候換一個戰術
模式，靠**跨回合**換模式脫困。

remake 照這個骨架實作，三處仍是近似，畫面上標 PROVISIONAL AI：

- **候選名單怎麼來**：原版由 overlay-25 `010Ah:00C0h` 填進 `DS:6CD7h`
  ——`0912h` 以射程當預算、方向不限地搜一遍，再篩掉不是對面陣營的
  （見下面那一節）。remake 仍借用 spec 059 的鄰接反應搜尋代替，差別在
  成本模型：原版走的是 `TraceMovement` 的半格成本，remake 是鄰接展開。
  挑法本身已經照原版——目標跨回合黏著，重挑時從名單裡擲骰隨機挑。
- **五個方向多一道距離閘門**：原版只問進不進得去，remake 另外要求那一步
  離目標更近（用 `tacticalStepDistances` 的繞路步數，所以繞牆仍算前進）。
- **五個方向都不合用時多一個繞路備案**：八個方向裡挑離目標最近的。

後兩項是同一件事的兩半，擋的是同一個坑：貼著牆的怪物會挑到 ±2 那兩個往旁邊
走的方向，下一步又走回來，一整回合原地打轉。原版靠**跨回合**換模式脫困，
照抄會讓怪物在死路裡卡上好幾回合——實測過整場打不完（`TestPassiveCombatTerminates`
打到第 3334 回合隊伍還活著）。加上這兩道之後，同一場從 2.49 秒打不完變成
0.54 秒收尾，擁擠盤面那一條從 24.9 秒降到 2.5 秒。

## overlay-09 entry 1：一隻怪物的一個回合

它是一條**「依序試各種行為，誰先動就停」**的鏈：

```
0015h  acted = entry 7（0FC8h）
0027h  overlay-25 entry 21（1830h）
002Ch  記錄 +10Dh 為 0 時：acted = overlay-25 entry 34（266Dh）
0045h  mode = runtime 子結構的 +15h
0054h  mode 落在 1..4 而且 骰(1,4) 不是 1 → 沿用（跳到 00A6h）
0060h  其餘一律重擲：骰(1,8) 擲出 8 → mode = 骰(1,2) + 4，否則 mode = 骰(1,4)
00A6h  寫回 +15h
00B5h  還沒動 → acted = entry 8（10DDh）
010Fh  還沒動 → entry 3（03E3h）成立時交給 overlay-25 entry 34
012Eh  runtime +0 非零 → overlay-22 entry 5（0C14h）再交給 entry 34   ; 開始施法的那一條
0169h  還沒動 → entry 2（0203h）＝ 轉變不死生物（spec 111）
0187h  還沒動 → entry 4（053Eh）＝ AI 挑法術（見〈entry 4〉）
019Bh  都沒動 → entry 9（13D5h），接著迴圈：entry 7 → 37B8h 挑目標 → entry 5 接近／entry 6
```

所以**每隻怪物身上帶一個戰術模式**（runtime `+15h`，值 1..6）。
1..4 這四個模式有四分之三的機會留到下一回合；5 與 6 每次都會被重擲掉。
重擲時的 `骰(1,8)` 只用來決定走哪一支——擲出 8（八分之一）才取 `骰(1,2) + 4`
得到 5 或 6，其餘七次都重新取 `骰(1,4)`。所以四個「試探型」模式各佔 7/32，
兩個「橫掃型」的各佔 1/16。

實作在 `gamepack.RollTacticMode`。

entry 2（`0203h`）是**轉變不死生物**那一支：runtime `+11h` 為 0（這一回合還沒
試過）且記錄 `+96h`（牧師等級）大於 0 時，交給 overlay-13 entry 13（`1352h`）
挑一隻要轉的目標，再由 entry 12（`116Ah`）擲骰執行。矩陣、列的折疊規則與
判定寫在 [spec 111](111-turn-undead.md)。

## 接近用的候選搜尋：`0912h` 早就解完了

entry 11（`0255h`）呼叫的 `0138h:003Eh` 是 **overlay-31 entry 6（`0912h`）**，
而那一支在 **spec 056 已經逐條閉合，也已經實作成
`internal/combat.NearbyCells`**：展開雙方佔格、過朝向弧、走 `TraceMovement`
取最小成本、朝向未指定時自 0 起找第一個成立的方向。

它前半用的 `013Dh:002Ah` 是 overlay-32 的 `0000h`：

```
000a  [bp+10h]（體型類別）為 0 → 回 false
0012  di = 體型 × 8 + 索引 × 2
0028  *[bp+0Ah] = DS:[2858h + di]      ; dx
0048  *[bp+06h] = DS:[2859h + di]      ; dy
0052  dx 為負 → 回 false
```

那張表就是 spec 056 的**佔格偏移表**（折疊常數 `2858h`、實際起點 `DS:2860h`、
每列 8 bytes、`0FFh` 代表該列到此為止）：體型 1 一格、2 直向兩格、
3 橫向兩格、4 是 2×2。原始位元組重新量過一次，逐位元組相符。

所以「原版先列出目標周圍可站的格子再挑」這件事，**共用機制本身不缺**，
缺的是敵方回合怎麼用它。

### entry 11（`0255h`）是「這一格旁邊有沒有自己人」

```
025Fh  push X、Y
0272h  push 型別表[型別 × 16 + 31A3h]        ; 體型類別
0279h  push 0FFh                              ; 朝向不指定
027Bh  push 1                                 ; 成本預算 1 ＝ 貼身
027Fh  push DS:6674h                          ; 結果表

```

`23F5h` 整支只有一件事：`f(記錄) = (記錄[+10Eh] == 0) ? 1 : 0`，也就是
**那一方的對立陣營值**。所以「`+10Eh` 不等於 `23F5h(自己)`」＝「跟自己同一邊」。
`0255h` 回的是「以這個體型站在 (X, Y) 時，貼身範圍內有沒有自己人」。

型別表 `31A3h + 型別 × 16` 的 `+0` 是體型類別；同一張表的 `+1`

## entry 7（`0FC8h`）是玩家打斷敵方回合

它不是行為，是**每一隻怪物動之前先看玩家有沒有按鍵**：

```
0fd2  0512h:02FAh()        ; 有按鍵嗎？沒有就回 0
0fde  026Bh:0048h()        ; 讀鍵碼；回 0 就再讀一次（擴充鍵的第二個位元組）
0ff4  鍵 == 32h（'2'）→ 把 DS:6D23h 反相，印 "Magic On" 或 "Magic Off"
103e  鍵 == 20h（空白）→ 走 DS:5CF4h 的整個串列，把 +84h < 80h
                          而且 +10Ch != 1 的記錄的 +10Fh 清成 0
```

兩段字就內嵌在同一顆 overlay：`0FB5h` 是 `Magic On`、`0FBEh` 是 `Magic Off`。
所以：

- **`DS:6D23h` 是「電腦幫我放法術」的開關**，戰鬥中按 `2` 切換。
- **空白鍵把控制權交回玩家**：`+10Fh` 就是 overlay-08 entry 3 拿來分派的那個
  旗標（非零走 AI），清成 0 之後那一隻改由玩家下指令。
  `+84h` 的位元 7 與 `+10Ch == 1` 是兩個例外，不會被交回。

## entry 8（`10DDh`）是士氣

```
10e7  entity[+14h] = 0
10f4  0100h:0066h(記錄)                     ; 先清掉 4Ah／4Bh 兩個效果
10ff  entity[+10h] != 0 → entity[+14h] = 1，印 "is forced to flee"，這一隻的
                          回合就結束
113e  記錄 +84h <= 7Fh → 直接返回            ; 位元 7 沒立＝這一隻不做士氣判定
114c  DS:6783h = (記錄 +84h & 7Fh) × 2       ; 士氣值
115d  > 66h（102）→ DS:6783h = 0             ; 太高就當作不會逃
1169  0100h:002Fh(群組 11h, 記錄)            ; 讓效果調整士氣（spec 112）
1185  掉血比例 = 100 − (+11Bh × 100 ÷ +32h)  ; 目前生命 ÷ 生命上限
119d  士氣 >= 掉血比例 而且 士氣 != 0 → 返回  ; 過關，不逃
11b0  否則士氣改成 DS:6D22h，再問一次群組 11h
11ca  士氣 >= 100 − [DS:4937h]+58Ch 而且 != 0 而且 +10Eh == 0 → 返回
```

所以士氣是**兩關**：先比自己掉了多少血，過不了再用另一個基準值比隊伍的
`+58Ch`。`+84h` 的位元 7 是「這一隻做不做士氣判定」，低七位 × 2 才是士氣值。

`+11Bh` 是**目前生命值**（`+32h` 是上限）——這一段的百分比算式就是證據。
神殿的起死回生與石化解除把它寫成 1，所以那兩項是「活過來但只剩一點」
（spec 115）。

字串在 `10C0h`（`is forced to flee`）與 `10D2h`（`Surrenders`）。
所以 `entity[+14h]` 是「這一隻正在逃」、`entity[+10h]` 是士氣判定的結果。

`0100h:0066h` 是 **overlay-24 entry 14（`103Bh`）**：一個跑兩圈的迴圈，把
`DS:0C38h` 與 `DS:0C39h` 兩個代碼——**`4Ah` 與 `4Bh`**——交給 overlay-24
entry 2（`0028h`）。entry 2 是**移除效果**：

```
0028  f(記錄: far; 代碼: byte; 節點: far)      ; retf 0Ah
002e  節點為 NULL → 從記錄 +7Fh 的串列頭找第一個代碼相符的節點
0074  找不到 → 直接返回
007f  節點 +4 非 0 → 先以**模式 1** 呼叫 entry 1，讓那個代碼自己的處理常式
        跑一次收尾（`014Dh` 用的是模式 0）
00a0  把節點從串列摘掉：是頭就改 +7Fh／+81h，否則沿串找前一個接過去
0119  RTL 的 FreeMem（`5BBh:364h`）釋放 **9 bytes**
```

所以效果節點是 9 bytes：`+0` 代碼、`+4` 「有收尾常式」旗標、`+5`／`+7` 下一個
的遠指標（spec 059 讀過 `+0` 與 `+5`，這裡補上長度、`+4` 與 `+81h` 那一半）。
士氣那一支因此是「先把 `4Ah`／`4Bh` 這兩個效果清掉，再看 `entity[+10h]`」。

`4Ah` 與 `4Bh` 正是 139 個代碼裡**唯二處理常式不在 overlay-12 的**
（在 overlay-13，spec 112 的表）。

`entity[+10h]` 這個旗標與**轉變不死生物**共用：`116Ah` 轉變成功時寫的就是它
（spec 111），而這裡讀到非 0 就印 `is forced to flee`——轉變在原版的實作就是
「讓那一隻進入被嚇跑的狀態」，不是另一套機制。

走的是記錄 `+C8h` 的物品串列、查的是物品型別表（spec 065：那張表的真身在

| `物品 +3Dh <= 0` → 跳過 | 沒有可用的編號 |
| `物品 +3Eh >= 80h` → 跳過 | `+3Eh` 的語意還沒對 |

`START.EXE` 掃過所有 disp16 形狀，寫它的只有 overlay-07 `025Bh`（寫 0），
讀它的四處（overlay-08 `073Bh`、overlay-09 `0436h`、overlay-15 `0373h`、
overlay-19 `0F9Ch`）全都只跟 0 比。與 `DS:43A0h` 是同一個形狀——留著但沒有
人把它設起來。（唯一的例外是某個整塊複製，那與 spec 114 的 `+5A4h` 是同一
個未解形狀。）

### 什麼時候施法（exact）

entry 1 的鏈上它排在 entry 3（用物品）、開始施法的那一條（`012Eh`）與 entry 2（轉變不死
生物）之後、追擊目標（`37B8h`）之前：**放得出法術的一隻不會先走路**。它回傳非零，這一隻
的行動就結束；回 0 才往下走接近迴圈。

```
0548  runtime +1 非零才收清單：                    ; 26 80 7D 01 00
0557    i = 0..14h：記錄 +17h+i 非零就依序收進清單   ; 26 80 7D 17 00 / 76 1B
0596  門檻 = 7                                     ; C6 46 E5 07
059A  次數 = Roll(1, 7)                            ; B0 01 50 B0 07 50 9A 48 00 00 01
05AC  清單是空的 → 不施
05B5  記錄 +84h <= 7Fh 而且 DS:6D23h == 0 → 不施    ; 26 80 BD 84 00 7F / 80 3E 23 6D 00
05C7  DS:[6772h + 23F5h(記錄)] <= 0 → 不施          ; 對面沒人站著
05DC  第 k 輪（k = 1..次數）：
05EE    擲三次：號碼 = Roll(1, 清單長度)；02EAh(記錄, 清單[號碼−1], 門檻) 成立就收下
063A    門檻 −1
0642  收下了 → overlay-13 entry 19（23F9h）(法術, 1, &結果)；結果就是回傳值
```

- **runtime `+1` 是「這一回合還能施法」**：每回合開頭 overlay-13 entry 1 `001Eh` 設成 1；
  受傷的那一刻 overlay-13 `04F6h` 清成 0（傷害 > 0 才清），沉默（效果 15h，overlay-12
  entry 22 `076Fh`）與咳嗽（1Eh，entry 29 `0AC0h`）也清。overlay-08 `072Fh` 也讀它
  （玩家指令那一側，還沒細讀；remake 玩家的 C 目前不看它）。
- **法術陣列從記錄 `+17h` 起 21 格**。怪物的法術就放在 `+18h` 起（八個怪物檔掃過：
  LEVEL 3 MU mon2/94 是 `00 0F 15 22`、LEVEL 6 MU 是 `00 0F 0F 15 15 22 20 2F 2F`），
  所以 spec 070 的 `+1Fh` 那 13 格是這個陣列的後段。比的是整個 byte，第 7 位立著的格子
  （還沒記完）也收進清單。
- **Magic On／Off 只管隊員**：`+84h >= 80h` 的（怪物全部是 FFh 或 B2h；隊伍裡的 NPC）不看

### 挑法術：`02EAh`（exact）

`f(記錄, 法術, 門檻)`，讀的是參數表（spec 074）以前列為 DRAFT 的 `+0Dh`：

```
02F4  表[法術].+0Dh（31A1h）< 門檻 → 否           ; 8A 85 A1 31 / 3A 46 06 / 73 03
030B  法術 != 3 而且 +0Eh（31A2h）== 0 → 是       ; 打自己，不必找人
0323  法術 == 3（治療輕傷）：overlay-13 entry 17（1BF0h）找得到 → 是
0344  n = 010Ah:00C0h(記錄, overlay-22 entry 3(法術))  ; 射程內的敵人（246Dh）
035C  n == 0 → 否
036D  +0Fh（31A3h）== 0 → 是                      ; 不是範圍法術
0380  對名單上每一個敵人：0255h(它的 X, Y, 法術) 成立 → 否
03D6  → 是
```

`+0Dh` 是 **AI 的優先度**，值 0..7：催眠、定身、臭雲、火球、閃電 7，魔法飛彈與魅惑 6，
解除魔法 5，治療輕傷 1；`+0Bh` 為 0 的營地法術全部是 0（`TestAISpellFieldsFromTheOriginalTable`）。
門檻從 7 開始、次數骰擲幾就降幾輪，所以最低降到 1——**優先度 0 的永遠不放**，而優先度 7
的第一輪就挑得到。overlay-22 entry 3（`071Dh`）是射程：戰鬥中 `+2 + +3 × 施法者等級`，
0 而 `+6` 非零墊成 1、FFh 當 1（`SpellParameters.Range`）。

`0255h` 是巢狀程序，前面已經讀過形狀：以那個敵人的位置為中心、體型 1、預算是 `+0Fh`，
跑一次 `0912h`，收到的人裡有跟施法者同一邊的（`+10Eh` 不等於 `23F5h(DS:5CF0h)`，施法者
自己也算）就回 true。所以**範圍法術只在「每一個射程內的敵人周圍都沒有自己人」時才放**。

`1BF0h`（治療輕傷找誰）：方向 0..8（`DS:274Ah`／`2753h`，第 9 項是原地）逐格看，站著的是
自己人而且目前生命（`+11Bh`）低於上限（`+32h`），比目前挑到的更少血就換（`1CBFh`）；
輪到施法者自己那一格時只要低於上限一半也換（`1CC4h..1CF9h`）。腳下沒人、地形是 1Fh 的
格子另走 `DS:6634h` 那張每筆 7 bytes 的表（`1D1Ah..1DA6h`，看起來是倒地的人）——**這一支
remake 沒有做**。

### remake 的對應

`internal/gamepack/spell_ai.go`（`ChooseAISpell`、`AIPriority`／`CastingCost`／
`CampOnly`／`TargetsCaster`、`AIDisablingEffects`）與 `cmd/pool-game/foe_cast.go`

送鍵，`TestStagedMagicUserCastsInANaturalFight` 用真的 mon2/94 記錄走建 roster 那一條。

與原版不同、寫明的幾處：

| 原版 | remake | 理由 |
|---|---|---|
| entry 3 擲完次數骰會掃物品鏈 | 只擲次數骰 | 怪物的物品鏈還沒載（`AttackRange` 那則註解），隊員用物品也還沒接 |
| runtime `+1` 在受傷當下清掉 | 輪到牠時比「回合開頭的生命值」 | remake 的傷害分散在好幾支；同一回合先補血再受傷、沒低過開頭的會漏 |
| 開始施法中受傷，當下印 "lost a spell" | 輪到牠時才印、才清 | 同上；清掉的格子與之後的行動相同 |
| 挑 `(模式 & 3) + 1` 個目標 | 骰照擲，只交第一個給 `castSpell` | 玩家那一側也一次只作用在一個目標上 |

| 第 7 位立著的格子拿去查表（讀到表外） | 當作不成立 | 表外那一格讀出什麼沒有追 |
| `1BF0h` 的倒地那一支 | 不做 | `DS:6634h` 那張表 remake 沒有 |
| entry 2 轉變不死生物在 entry 4 之前 | 沒有接 | AI 的轉變不死生物另案 |

## entry 5（`0B3Ch`）是接近迴圈

`07E8h` 不是由 entry 1 呼叫的，是由 **entry 5** 呼叫，一回合裡呼叫很多次。
開場先清三個全域，然後兩段迴圈：

```
0b42  DS:439Eh = 8   ; 上一步的方向，8 代表還沒走過
0b47  DS:439Fh = 0   ; 「卡住」的次數
0b4c  DS:43A0h = 0   ; 只有這一處，全程式沒有讀取端
0b9f  逃跑迴圈：runtime +14h 非零、+6 > 0、0 < +3 < 14h → 07E8h(記錄)，重來
0c12  輪數 +1；超過 14h（20 輪）就收工
0c3e  射程 = 手上武器（記錄 +CCh）型別的 DS:[54ECh + 型別 × 16] − 1，
        0 或 0FFh 一律當 1                       ; 近戰就是一格
0c7b  目標 = runtime +0Ah 的遠指標；+10Dh 或 +10Eh 為 0 就作廢
0d4b  n = 010Ah:00C0h(記錄, 射程)                ; 射程內有幾個候選
0d5d  n == 0 → 0096h:00A7h(記錄, 0FFh, 0, 0) 成立就走一步（07E8h），
                否則交給 entry 6
0d97  n != 0 → 骰(1, n) 取一個，DS:[6CD7h + 擲出的號碼] 得索引，
                DS:[6517h + 索引 × 4] 得那一隻的記錄，接著打
```

`DS:43A0h` 跟它前面兩個是一起清的，但**只有寫、沒有讀**。三十六顆 overlay
加 `START.EXE` 掃過 `A0/A1/A2/A3` 的絕對定址與所有 disp16 的 modrm 形狀，
`43A0h` 只出現在這一行（overlay-17 `1E7Eh` 與 overlay-18 `009Ch` 那兩筆是
位元組湊巧對上的假命中，前者是 `jnz`，後者是 `push si` 接 `mov al, ds:4943h`）。
旁邊的 `439Eh`（上一步的方向）與 `439Fh`（卡住次數）都讀得到，所以這一段是
三個純量旗標而不是陣列——`43A0h` 在這一版裡就是清掉之後沒人用的格子。

兩件事因此定了下來：**搆得到就打、搆不到才走**，而且**打誰是從射程內的
候選名單裡擲骰隨機挑的**，不是挑最近或最弱的。射程來自武器型別記錄的
`+0Ch`（spec 065 的那張表）。

`runtime +0Ah`／`+0Ch` 是**目標的記錄遠指標**，不是座標。追擊的目標由
`0096h:00A7h`（overlay-13 entry 27，`37B8h`）寫進去，見下一節。

## 追誰由 overlay-13 entry 27（`37B8h`）決定

`0096h:00A7h` 就是它，簽章是 `f(記錄, 射程, 放寬, 強制重挑)`——
entry 5 用 `(記錄, 0FFh, 0, 0)`，走一步的那一支用 `(記錄, 0FFh, 1, 0)`。

```
37ca  舊目標 = 記錄 +108h 的 +0Ah                ; 遠指標
37de  強制重挑 != 0 → 丟掉
37ec  舊目標 +10Eh == 自己 +10Eh → 丟掉          ; 同一邊
37fe  舊目標 +10Dh == 0 → 丟掉                   ; 不在場
3809  1087h(記錄, 舊目標) 非零 → 留著
382f  目標非 NULL → 找到了，收工
3872  次數 = 14h                                 ; 最多試二十次
3876  n = 010Ah:00C0h(記錄, 射程)                ; 候選填進 DS:6CD7h
38a6  重複：號碼 = 骰(1, n)
38b5    DS:[6CD7h + 號碼] == 0 → 重擲             ; 這一格已經被劃掉
38c6    索引 = DS:[6CD7h + 號碼]；目標 = DS:[6517h + 索引 × 4]
38e5    放寬 != 0 而且 DS:6674h 的 +6 != 0 → 直接收下
38f6    否則 1087h(記錄, 目標) 非零才收下
390a    收下：記錄 +108h 的 +0Ah／+0Ch = 目標
3925    不收：DS:[6CD7h + 號碼] = 0，掃一遍名單還有沒有剩的，
          有就重擲，沒有就 n = 0
3973  一輪挑不到 → 把「放寬」打開（DS:6674h 的 +6 = 1）再跑一輪
3980  收尾把 DS:6674h 的 +6 清回 0，回傳有沒有挑到
```

三件事因此定了下來：

1. **目標會跨回合黏著**——還在場、還是對面的、還過得了 `1087h`，就不重挑。
2. **重挑是從候選名單裡擲骰隨機挑**，挑到不能打的就把那一格劃掉重擲，
   最多二十次。不是挑最近的，也不是挑最弱的。
3. **兩輪制**：第一輪全被 `1087h` 擋掉時，第二輪把判定放寬再挑一次。

remake 三點都接上了（#65）：目標存在 `tacticalState.FoeTargets`，沿用前過
`attackVetoed`（`1087h`）；重挑用 `rollDice(1, n)`，劃掉過不了的、最多二十次；
第一輪挑不到就以 `IgnoreTerrain`（`+6` 的放寬）再挑一輪。`1087h` 的四個代碼都照原版
（`attackVetoed`，spec 059）。`0D97h` 搆得到時的 `骰(1, n)` 也接上了：
原版骰流收據（`dosgolem-deployment-peek-*.json`）裡 d20 前面緊接一擲 d1 的有 23 次，
名單只剩一個人也照擲。

### `1087h`：候選能不能打

```
1091  目標為 NULL → 回 false
109c  目標就是自己 → 回 true
10b1  DS:677Ch = 0
10b6  0100h:002Fh(1, 目標)                       ; overlay-24 entry 3（02E2h）
10c4  DS:677Ch != 0 → 1117h
10cb  存下 記錄 +108h 的 +0Ah
10df  暫時把 +0Ah／+0Ch 換成這個候選
10f4  0100h:002Fh(0, 記錄)                       ; 再問一次，這次對自己
1102  還原 +0Ah／+0Ch
1117  DS:677Ch 仍為 0 → 回 true，否則 false
```

所以它是**雙向問一次** overlay-24 entry 3：先對候選、再把自己的目標暫時換成
候選之後對自己，兩次都沒有把 `DS:677Ch` 立起來才算能打。

`02E2h` 那 2051 bytes 讀完了，內容比看起來單純：它是一個 20 路的 `case`，
每一路就是一串效果代碼，逐一交給 `014Dh` 問「這個效果影響得到這筆記錄嗎」。
群組 1 是 `3Fh 25h 19h 47h`（問候選），群組 0 只有 `7Eh`（問自己）。
命中的代碼會被送進 `DS:6786h` 那張以代碼為索引的處理常式表，而 `DS:677Ch`
是那些處理常式共用的回報格。表查完之後「能不能打」就完全展開了：群組 1 的
`19h`（目標沒有 `18h` 就否決）、`25h`（目標先攻分數還大於 0）、`47h`（一律
否決）會立起 `677Ch`，`3Fh` 指到一支空常式所以不會；群組 0 的 `7Eh` 走的是
自己當下目標的物品串列——`1087h` 先把 `+0Ah`／`+0Ch` 換成候選就是為了它。
細節與整張群組表在 [spec 112](112-effect-code-dispatch.md)。

### `010Ah:00C0h`：候選名單怎麼填進 `DS:6CD7h`

`010Ah` 是 overlay-25（spec 109），stub `00C0h` → entry `(0C0h − 20h) ÷ 5 = 32`
→ code offset **`246Dh`**。簽章是 `f(記錄, 射程) → 候選數`（`retf 6`）。

```
246d  f(記錄:far, 射程:byte)
2473  x    = 013Dh:006Bh(記錄)                   ; overlay-32 entry 15 → 5E85h 的 +0
247f  y    = 013Dh:0070h(記錄)                   ; overlay-32 entry 16 → +1
248b  推 射程、推 0FFh（不限方向）
2494  體型 = 013Dh:0075h(記錄)                   ; overlay-32 entry 17 → +3
24a0  0138h:003Eh(x, y, 射程, 0FFh, 體型,
                 戰術地圖遠指標)                  ; overlay-31 entry 6 ＝ 0912h
24ad  n = DS:6678h                               ; 它填出來的筆數
24b3  寫入游標 = 0
24b7  n == 0 → 收工
24d5  對 i = 1..n：
24db    對立陣營值 = overlay-25 entry 30（23F5h）(記錄)
24e1    索引 = DS:[6676h + i×3]                  ; 結果表每筆 3 bytes
24f9    目標 = DS:[6517h + 索引×4]               ; combatant 遠指標表
24fd    目標 +10Eh != 對立陣營值 → 跳過
2506    游標++；Move(第 i 筆, 第 游標 筆, 3)      ; 05BBh:1692h，RTL 的 Move
253e  n = 游標；DS:6678h = 游標                   ; 壓實後的筆數
2550  對 i = 1..n：DS:[6CD7h + i] = DS:[6676h + i×3]
2588  回傳 n
```

三支 `013Dh` 的取值都是同一個形狀（overlay-32 entry 15／16／17，各 40 bytes）：
先用 entry 18（`0C61h`，spec 058 已讀）把記錄換成 1-based 的 combatant 索引，
再取 `DS:5E85h` 那張每筆 4 bytes 的戰場位置表——`+0` X、`+1` Y、`+3` 體型類別
（spec 056）。所以推給 `0912h` 的前五個參數是「我在哪、走得動多遠、不限方向、
我多大」，最後推的是 `DS:6674h` 的戰術地圖遠指標（segment 在 `6676h`）。

四件事因此定了下來：

1. **搜尋本身是 `0912h` 做的**（overlay-31 entry 6，spec 057 的 `TraceMovement`
   成本模型）。射程原封不動當預算、方向給 `FFh`（不限），與火球術的收人算法
   同一支——**移動、射程、範圍法術與 AI 找目標共用一個成本模型**，這裡是
   第四個用例。
2. **中繼表就是 spec 056 的鄰近查詢結果表**：`DS:6676h` 是折疊常數，元素自
   `DS:6679h` 起、每筆 3 bytes（`+0` combatant 索引、`+1` 成本、`+2` 攻擊該
   目標所需的朝向），筆數在 `DS:6678h`。**`6676h` 同時是戰術地圖遠指標的
   segment 欄位**，兩者相鄰但不是同一個結構。
3. **篩的是陣營**：只留 `+10Eh` 等於「對立陣營值」的。那個值由 overlay-25
   entry 30（`23F5h`）算，就是 `(記錄[+10Eh] == 0) ? 1 : 0`（spec 109 的正對照）。
   留下來的**原地壓實**，用 RTL 的 `Move` 搬三個 byte——所以成本與朝向那兩個
   byte 也一起留著，只是 `37B8h` 沒有用到。
4. **最後才抄成 `DS:6CD7h`**：一筆一個 byte，只留索引，1-based。這正是
   `37B8h` 讀的那張表——`DS:[6CD7h + 號碼]` 為 0 代表「這一格已經被劃掉」，
   非 0 就拿去查 `DS:6517h + 索引 × 4`。兩邊的讀法逐格吻合。

## entry 13（`07E8h`）是「走一步」

`0868h` 那個 `runtime +3` 是**先攻分數**，每回合由 overlay-13 entry 1 重擲
（spec 052、spec 062）。分數在這一輪被扣光的怪物不走路，交給 entry 6 收工。

`087a` 那個 `記錄 +2Fh == 5` 不是未知旗標：`+2Fh` 是**複合職業碼**，跟玩家
角色記錄同一個欄位（`gamepack.ClassCodeOffset`、`internal/character` 的
`offsetClass`、spec 085、spec 097），5 是**純法師**。所以那一條是
「不逃跑的純法師不走路，交給 entry 6」。

怪物記錄用的是同一套編碼：八個怪物檔的 172 筆記錄裡只出現七個值，全部都是
建角目錄裡挑得到的合法職業碼——0 牧師 10 筆、2 戰士 134 筆、5 法師 15 筆、
6 盜賊 9 筆，另有 9（牧師／戰士／法師）2 筆、11（牧師／法師）1 筆、
15（戰士／法師／盜賊）1 筆。`TestMonsterClassCodeIsTheCharacterClassCode`
釘住這一條，並且拿四隻叫得出名字的當正對照。

```
07e8  f(記錄)                                    ; retf 4，一個遠指標
083c  entry 7（0FC8h）回非零 → 返回              ; 玩家打斷
084d  runtime +6 ÷ 2 <= 0 → 交給 entry 6         ; 沒有腳程了
0868  runtime +3 <= 0 → 交給 entry 6            ; +3 是先攻分數（spec 062）
087a  runtime +14h == 0 而且記錄 +2Fh == 5 → 交給 entry 6  ; 不逃跑的純法師
0896  runtime +14h != 0（正在逃）→ 08C5h
08a5  否則 基準方向 = 0096h:0093h(記錄, 目標記錄)  ; overlay-13 261Bh
08c5  逃跑時：模式 = 骰(1,2)
08dc      基準 = 朝向 − ((朝向 + 2) mod 4) div 2   ; 朝向在 DS:6A0Dh（spec 106）
08fd      記錄 +10Eh == 0 → 基準 += 4
0913      基準 mod= 8
092a  步 = 1；「步 < 6 而且還沒走成」時重複：
093a    成立 = 066Eh(記錄, 步, 基準, &出界)
0951    成立 → 跳出迴圈
0955    正在逃而且出界 → 成立 = 0096h:0043h(記錄)   ; 逃出盤面
097a    步 += 1
09b0  方向 = (基準 + DS:[02ACh + 模式 × 5 + 步]) mod 8
09e7  步 != 6 而且 (方向 + 4) mod 8 != DS:439Eh → 0A88h   ; 一切正常
0a0a  否則：DS:439Fh += 1；模式 = (模式 mod 6) + 1
0a30    439Fh <= 1 → 0A88h                        ; 第一次仍然走
0a37    runtime +0Ah／+0Ch 清成 0                  ; 忘掉目標
0a49    439Fh <= 2 → 0A63h，否則 runtime +6 = 0，收工
0a63    0096h:00A7h(記錄, 0FFh, 1, 0) 不成立 → 交給 entry 6
0a88  步 < 6 → DS:439Eh = 方向，否則收工
0aa3  013Dh:0066h(記錄, 方向, 0, 0)               ; 真的移動
```

三條規則從這裡定下來：

1. **步數 1..5 依序試，第一個進得去的就走**，不比較距離。
2. **走回上一步的反方向算「卡住」**：第一次照走，第二次起忘掉目標，
   第三次起這一隻這一輪不再動。五個方向全不通也走同一條路——但那只是這一次
   `07E8h`（步 = 6 在 `0A88h` 不成立，這一輪不動），entry 5 的迴圈不看它的回傳值
   （`0BD3h`／`0D82h` 呼叫完就跳回去），下一輪用換過的模式再試。
3. **模式在卡住時才換**，換法是 `(模式 mod 6) + 1`。
4. **每一輪開頭看腳程**：`084Dh` 的 `runtime +6 ÷ 2 <= 0` 就交給 entry 6，剩 1 點算零步。

remake 的 `foeTurn` 2026-09-16 起照這三條走：五個偏移依序試、第一個進得去的就
走、不比距離。以前多了兩條非原版備案（「要離目標更近」的 BFS 篩選、八方向繞路），
dosgolem 衛兵那一場的收據（spec 061，`dosgolem-deployment-peek-guards.json`）量到
原版後排的獸人沿著隊伍北側一路擠上來（34：(19,5)→(23,4)→(26,4)），remake 的卻
一步不動——那兩條把它們鎖住了。拿掉之後同狀態的後排走的是同一條走廊、到同一格
（`TestDeploymentMatchesTheSlumsReceipts` 的 log）；僵局仍由 endRound 的安全閥兜底
（非原版，有觸發計數）。

規則 2 的「第二次」remake 也照 `0A37h`／`0A49h`：忘掉目標、當場從名單重挑一個再走
（`0A63h` 挑不到才收工），第三次起才清腳程。三筆收據的逐步快照（`actions`，dosgolem
`-trace-peek`）量到原版一隻怪一輪內先往東再往西再換方向，就是這一條在動。

### 骰流對回去之後（2026-09-16）

dosgolem `shots -trace-call 5BB:C94` 把 Turbo Pascal `Random(n)` 的每一次呼叫記下來

- `d100 × 在場人數` 是選下一個行動者的決勝骰（spec 052 `0124h`），每個行動者（含隊員）
  之前都擲一輪。
- 模式：`0054h` 的沿用骰 d4 只在模式落 1..4 時出現，`d8 (d4|d2)` 是重擲；第一次行動的怪
  模式是 0，一律重擲。
- `d7 d7` 每一回合都有、在模式與挑目標之間：前一顆是 entry 3（用物品）`03FFh` 的次數骰，
  後一顆是 entry 4（挑法術）`05A0h` 的次數骰，兩顆都在任何閘門之前擲（見〈entry 4〉）。
  remake 由 `foeCastPhase` 在同一個位置擲；`TestFoeWalkReproducesEveryOriginalAction` 把
  骰流裡那一對原樣餵進去，三場 40 個動作的 d7 請求與骰流逐顆對上（零筆錯位）。
- 挑目標的骰面 `n` 就是**對面還站著的人數**（5 → 死一個變 4 → 3 → 2 → 1），劃掉重擲的
  會連擲幾顆。

`TestFoeWalkReproducesEveryOriginalAction` 拿三場 40 個原版動作逐一擺盤重走：模式、

## 基準方向就是目標的方位

`0096h:0093h` 是 **overlay-13 entry 23（`261Bh`）**，spec 098 已經解過：
取雙方的座標，自方向 0 起遞增，回第一個讓 overlay-31 `0579h` 的攻擊弧
成立的方向。兩支都已經實作成 `combat.RequiredFacing` 與
`combat.FacingArcContains`，這次逐分支重讀一次，八個方向的條件與現有實作

方向表本身在 `DS:274Ah`（X 位移）與 `DS:2753h`（Y 位移），各九項，
第九項是「不指定方向」的 (0, 0)：0 向上，順時針到 7。

## 戰術模式是一列方向偏移（`DS:02ACh`）

`066Eh` 把「步」換成方向：

```
067f  cx = [bp+0Ch]                    ; 步，1..5
068e  模式 = 記錄 +108h 的 +15h
0694  di = 模式 × 5 + cx
069d  al = DS:[02ACh + di]
06ab  ax = 基準方向 + al
06b3  除以 8 取餘數 → 0..7 的方向
```

也就是 **`方向 = (基準方向 + 表[模式 × 5 + 步]) mod 8`，步從 1 數到 5**。

表在 `DS:02ACh`（原始位元組取自 `START.EXE`，檔案位移＝`DS` 位移 ＋
`77B0h`）。**步是 1-based**，所以模式 `m` 實際用到的是
`02ACh + m×5 + 1` 起的五個 byte：

| 模式 | 五個偏移（原值）| mod 8 之後 |
|---:|---|---|
| 1 | `08 07 06 01 02` | 0、−1、−2、+1、+2 |
| 2 | `08 01 02 07 06` | 0、+1、+2、−1、−2 |
| 3 | `07 01 08 06 02` | −1、+1、0、−2、+2 |
| 4 | `01 07 08 02 06` | +1、−1、0、+2、−2 |
| 5 | `08 07 06 05 04` | 0、−1、−2、−3、+4 |
| 6 | `08 01 02 03 04` | 0、+1、+2、+3、+4 |

**六列兩兩成鏡像**：1 與 2 是「先往左試」與「先往右試」、3 與 4 是另一組
鏡像、5 一路往左掃、6 一路往右掃。這個對稱本身就是「步是 1-based」最強的
佐證——用 0-based 讀出來的六列沒有任何對稱可言。
`02ACh` 起的頭五個 byte 全是零，也與「模式從 1 起算」一致。

實作在 `gamepack.DefaultTacticOffsets`／`TacticOffsets.Direction`／
`NextTacticMode`，讀原始位元組的是 `ReadDOSTacticOffsets`。

算出方向之後，`066Eh` 就地試那一格：

```
06bc  013Dh:007Fh(記錄, 方向, &出界, &地形索引)   ; overlay-32 0CB9h
06d5  地形索引 == 0 → *出界 = 1，回 false          ; 走不到
06e5  有人           → 回 false                    ; 佔著了
06ee  al = DS:[2758h + 地形索引 × 4]               ; 格位類別表（spec 053／057）
0705  al >= entity +6 → 回 false                   ; 地形超出這一隻的能力
070e  否則回 true
```

所以每一步的判準是**佔用**與**格位類別對上這一隻的 `+6`**，不是距離。
回 false 的第一種情形（地形索引 0）代表那一格在盤面外，逃跑中的怪物就是
靠它跑出戰場。

## 查過但沒有讀取端

這幾個是**掃完之後確定沒有人用**的，不是還沒查：

- **型別表 `DS:31A3h + 型別 × 16` 的 `+1` 以後**。全 36 顆 overlay 加
  `START.EXE` 掃過所有 disp16 形狀，這張表只被存取四次（overlay-09
  `0272h`／`036Dh`、overlay-13 `1F29h`／`1F56h`），四處都是 `[di + 31A3h]`
  而 `di` 正好是 `型別 << 4`。16 bytes 的間距是真的（每一列內容都不同），
  但其餘 15 個 byte 沒有人讀。`+0` 幾乎都是 0、偶爾是 1，與「多數怪物佔
  一格、少數佔 2×2」相符。
- **`DS:43A0h`**：只有 overlay-09 `0B4Ch` 寫它一次（清成 0），沒有讀取端。
- **`[4933h]+1CAh`**：只有 overlay-07 `025Bh` 寫它一次（寫 0），四處讀它
  而且都只跟 0 比，所以那幾個閘門在這一版永遠不成立。

三者都留著同一個例外：某個整塊複製有可能把值填進去，而那與 spec 114 的
`+5A4h` 是同一個未解形狀。
