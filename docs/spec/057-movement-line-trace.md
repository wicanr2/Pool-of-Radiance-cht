# Spec 057：移動直線追蹤與每步成本

狀態：READY（走訪器、每步成本、方向索引、`0419h` 的控制流、
`PathByte1`／`PathByte2` 的用途）；DRAFT（地圖 record 前六個 byte）。
日期：2026-09-02。

## 為什麼需要這一段

spec 056 的 `0912h` 以 `sub_419` 判定「這個目標構不構得到、要花多少」，
並把回傳的成本寫進結果表。本規格閉合 `sub_419` 與它依賴的兩支共用常式。

## 走訪器：26 bytes 的 record

`0196h` 初始化、`02C4h` 前進一步，兩者都以遠指標收同一個 record：

| 位移 | 大小 | 內容 |
|---|---|---|
| +0 | 2 | 起點 X |
| +2 | 2 | 起點 Y |
| +4 | 2 | 終點 X |
| +6 | 2 | 終點 Y |
| +8 | 2 | 誤差項 |
| +0A | 2 | `dx = \|x1 − x0\|` |
| +0C | 2 | `dy = \|y1 − y0\|` |
| +0E | 2 | 斜走時的誤差增量 |
| +10 | 2 | 直走時的誤差增量 |
| +12 | 1 | X 方向正負號 |
| +13 | 1 | Y 方向正負號 |
| +14 | 2 | 目前 X |
| +16 | 2 | 目前 Y |
| +18 | 1 | 累積成本 |
| +19 | 1 | 這一步的方向索引 |

呼叫端只提供前四個欄位，其餘由 `0196h` 填。正負號取自 `0000h`，
那是一支回傳 −1／0／1 的 signum。

## 初始化：`0196h`

以較長的軸為主軸。令 `major = max(dx, dy)`、`minor = min(dx, dy)`：

```
誤差項     = 2 × minor − major
斜走增量   = 2 × (minor − major)
直走增量   = 2 × minor
目前位置   = 起點
累積成本   = 0
```

原版的判斷寫成 `if dx > dy`，因此 `dx == dy` 走的是「以 Y 為主軸」那一支。

## 前進一步：`02C4h`

主軸尚未抵達終點時走一格：誤差項非負就同時在副軸上走一格（斜走），
否則只走主軸（直走）。

| 走法 | 誤差項 | 成本累加 |
|---|---|---|
| 斜走 | 加斜走增量 | **+3** |
| 直走 | 加直走增量 | **+2** |

成本以半格為單位，所以直走是 2 不是 1。`+18` 是位元組，理論上會在 256 溢位；
原版沒有防護，實際預算遠小於此。

方向索引由 `DS:25D4h` 的 3×3 表查得，索引為 `(signY + 1) × 3 + (signX + 1)`：

|  | signX −1 | 0 | +1 |
|---|---|---|---|
| **signY −1** | 7 | 0 | 1 |
| **0** | 6 | 8 | 2 |
| **+1** | 5 | 4 | 3 |

這與 spec 056 的 `DS:274Ah`／`DS:2753h` 方向環完全一致，是兩張獨立資料互相印證。
沒有移動時兩個正負號都是 0，查到 8（無方向）。

回傳值是「這一步有沒有真的移動」。

## 直線追蹤：`0419h`（`138h:39h`）

`function(map: far ptr; var cost: word; var y, x: byte; fromY, fromX: byte): boolean`，
`retf 14h`。

地圖 record 以遠指標傳入：`+6` 是「跳過地形判定」旗標，格子自 `+7` 起、
列距 `32h`（50），第 (x, y) 格的位址為 `map + y×50 + x + 7`，內容是地形碼。
列距 50 與 spec 056 的 X 軸上限 49 一致。

格位類別表就是 spec 053 的 `DS:2758h` 那張 66×4，程式碼用折疊常數 `2759h`
（欄位 `PathByte1`）與 `275Ah`（欄位 `PathByte2`）。本規格閉合的正是這兩欄的
用途：它們只在直線追蹤裡被讀，是通行判定的兩邊。

流程：

1. `limit = cost × 2 + 1`。
2. 以 (fromX, fromY) → (x, y) 建走訪器；另取起點格的 Level。
3. 迴圈，每一輪先判定再前進：
   - 地圖 `+6` 為 0 時，目前格的 `PathByte2 > 起點格的 PathByte1` 就停；
   - 累積成本大於 `limit` 就停；
   - 走一步；走不動（已到終點）就成功結束。
4. 停下來時把目前格寫回 `x`、`y`，成本寫回 `cost`，回傳 false。
   成功時只寫回成本，回傳 true。

地形判定發生在每一輪的開頭，包含起點自己——起點不可通行時當場回 false。

原版另外建了第二支走訪器來取那個 `PathByte1`：它的兩個端點同高（都由起點格
算出），`dy` 為 0，逐步走訪不會改變它的目前 Y，所以那個值是常數。本規格與
實作直接用常數，行為等價。

## 尚未閉合

- 以出貨資料而言，`PathByte1` 66 筆全部是 0，所以「可通行」等價於
  `PathByte2 == 0`。這是資料的性質，不是程式的性質，不可寫死成判斷式。
- 地圖 record 的 `+0`..`+5`。
- `PresentationCode`（欄位 +3）的完整語意，見 spec 053。

## 結果排序：overlay-31 `002Eh`

`0912h` 收尾呼叫的就是它：對 `6674h` 結果表做交換排序（外層 i、內層 j > i，
逐對比較並交換）。j 排在 i 前面的條件是

- 成本較小；或
- 成本相同、朝向索引較小，**且** j 的 `朝向 mod 2` 不大於 i 的。

第二個條件讓四個對角朝向不會越過四個正向。這個比較關係不是全序，
所以重建時必須照原版的兩層迴圈逐對交換，不能換成一般的排序函式。

`002Eh` 沒有設定回傳值，`0912h` 直接把它的 AL 當成自己的回傳值；
唯一的呼叫端 overlay-25 entry 32 並不看那個值。

## READY 契約

1. 每步成本固定 2（直走）與 3（斜走），預算上限是 `budget × 2 + 1`。
   不得改成整數格數比較。
2. 誤差項與兩個增量照 `0196h` 的式子算，`dx == dy` 要走「以 Y 為主軸」那一支。
3. 判定順序是「先地形、再預算、最後前進」，且第一輪就會判起點格。
4. 走不完時要回報停下來的格子與當下成本，不可只回一個布林。
5. 類別表沿用 `gamepack.ParseCombatCellClassTable` 的 66 筆，不得在戰鬥層
   另建一份副本；程式也不得內建「`PathByte2 == 0` 即可通行」的捷徑，
   那只是出貨資料剛好如此。
6. 折疊基底 `2758h` 讓索引 0 與方向表尾端共用儲存空間，表尾的索引 64、65
   同樣與佔格表未使用的第 0 列重疊。照抄無妨，但不要賦予它們地形語意。
